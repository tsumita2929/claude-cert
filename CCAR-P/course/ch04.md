- 試験: CCAR-P ／ 分野3 統合（19%）／ タスク 3.3、3.4、3.5、3.6（番号は教材の便宜上のもの）

## 本文

### この章で学ぶこと

第4章は、分野3、統合の後半です。配点19%の分野3を、前の第3章と分け合います。この章の範囲は4つのタスクです。精度とレイテンシのトレードオフ、大規模なオブザーバビリティ、RAG のチャンキングとインデックス、そして検索戦略です。

**要点**
- 分野3 統合は19%で、最も配点が大きい
- この章は、精度とレイテンシ、モニタリング、RAG、検索戦略
- 統合の設計と認証・認可は第3章

### 精度とレイテンシは、測ってから決める

最初は、精度とレイテンシのトレードオフです。レイテンシとは、応答が返るまでの待ち時間のことです。Anthropic のドキュメントは、まず制約を付けずに、うまく動くプロンプトを作り、そのあとでレイテンシを減らすよう勧めています。先に削ると、最高の性能が分からなくなるからです。

減らす手段は、速いモデルを選ぶ、effort を下げる、プロンプトと出力を短くする、プロンプトキャッシングを使う、などです。ストリーミングは、利用者が感じる待ち時間を縮めます。

試験で問われるのは、構成を決めた根拠です。速くしたいから最小のモデルにする、では根拠になりません。実際のデータで精度とレイテンシを測り、要件を満たす中で最も軽い構成を選びます。必要な文書を切り捨てて速くする案は、誤答の定番です。

**要点**
- まず精度を出し、そのあとでレイテンシを削る
- 手段はモデル、effort、長さ、キャッシュ、ストリーミング
- 根拠は、実データで測った精度とレイテンシ
- 必要な情報を捨てる高速化は誤答の定番

### チャンクは、文脈が切れない単位で作る

次は、RAG の設計です。RAG は、検索で取ってきた文書の断片を、プロンプトに加えて答えさせる方式です。この断片を、チャンクと呼びます。

文書をチャンクに切ると、文脈が落ちることがあります。たとえば、売上が前の四半期から3%伸びた、という1文だけでは、どの会社の、いつの話かが分かりません。Anthropic の Contextual Retrieval という手法では、文書全体から見た短い説明を Claude に書かせ、各チャンクの先頭に付けてから索引を作ります。

チャンクの大きさ、区切る位置、前後の重なりも、検索の精度に影響します。決まった正解はなく、自分の文書と質問で試して決めます。

そもそも RAG が要らない場合もあります。知識ベースが小さいなら、全部をプロンプトに載せて、キャッシュを使うほうが簡単です。同じ記事は、その目安を20万トークン未満としています。

**要点**
- チャンクに切ると、文書の文脈が落ちることがある
- チャンクの先頭に、文書全体から見た説明を付ける
- 大きさ、区切り、重なりは自分のデータで試す
- 小さな知識ベースは、全部載せてキャッシュ

### インデックスは、文書の更新に追いつかせる

インデックスとは、チャンクを速く探すための索引です。よく使うのは2種類です。1つは、意味の近さで探す、埋め込みのインデックスです。埋め込みとは、文章の意味を数値の並びにしたものです。もう1つは、言葉の一致で探す、BM25 のようなキーワードのインデックスです。なお、Anthropic は埋め込みモデルを提供していないので、提供元を選んで比べます。

運用では、インデックスを文書と同じ新しさに保ちます。公式のサンプル問題に、文書の更新後、RAG が自信を持って誤答し始める例があります。モデルもレイテンシも変わっていません。まず疑うのは、検索とインデックスの段です。たとえば、インデックスの作り直しの失敗や、埋め込みの不一致です。変わったのは文書だけ、という事実が手がかりです。

**要点**
- 埋め込みは意味で、キーワードは言葉の一致で探す
- Anthropic は埋め込みモデルを提供していない
- 文書を更新したら、インデックスも追いつかせる
- 更新後の誤答は、まず検索とインデックスを疑う

### 検索の方法は、データの形と質問の型で選ぶ

検索戦略は、データの形と質問の型で選びます。意味で探す検索は、言い換えに強い反面、型番やエラーコードのような、文字どおりの一致を取りこぼすことがあります。キーワードの検索は、その逆です。両方の質問が来るなら、2つの検索を並べ、結果を順位で統合します。

さらに、候補を多めに取り、リランカーで絞る方法があります。リランカーは、質問との関連の強さで候補を採点し直すモデルです。先ほどの記事の評価では、チャンクの説明、キーワードの検索、リランカーを重ねると、検索の失敗率がおよそ3分の1になりました。その分、レイテンシとコストが増えます。ここも精度とレイテンシのトレードオフです。

一方、在庫や口座の残高のように刻々と変わる値は、検索に向きません。元のシステムに、ツールや API で問い合わせます。現在の状態を引くべき仕事を、検索に担わせていないか。公式の対策講座も挙げる観点です。

**要点**
- 型番やコードは、キーワードの検索が強い
- 2つの検索の結果を、順位で統合する
- リランカーは精度を上げ、レイテンシを足す
- 刻々と変わる値は、検索せずに元のシステムへ

### 見える化は、段ごとの追跡と品質の信号で作る

最後は、大規模なオブザーバビリティです。これは、システムの中で何が起きているかを、外から観測できる度合いのことです。LLM のシステムには、難しさが3つあります。1つ目は、同じ入力でも、毎回同じ動きをするとは限らないこと。2つ目は、失敗がエラーとして現れないこと。応答は正常に返り、答えだけが間違うのです。3つ目は、段が多いことです。検索、モデル、ツールのどこで崩れたかを、答えだけでは切り分けられません。

そこで、リクエストごとに、すべての段を1本につないで記録します。Anthropic のマルチエージェントの記事も、本番の全体を追跡したことで、失敗の原因を体系的に直せたと述べています。記録するのは、たとえば、返したチャンクとその出どころの文書、`request-id`、`usage` のトークン数、`stop_reason`、各段の所要時間です。

規模が大きいと、プライバシーも課題です。同じ記事では、会話の中身は見ずに、判断のパターンとやり取りの構造をモニタリングしました。また、レイテンシとエラー率だけのモニタリングでは、品質の崩れを見逃します。評価の指標とモニタリングの実務は、第5章で扱います。

**要点**
- LLM は非決定的で、失敗がエラーに現れない
- リクエストごとに、全段を1本につないで追跡する
- チャンク、`request-id`、`usage`、`stop_reason` を残す
- 会話の中身ではなく、判断のパターンをモニタリングする
- レイテンシとエラー率だけでは品質を見逃す

### ミニクイズ

それでは、ミニクイズです。

ある小売企業の社内向けの RAG で、商品の型番で質問すると、似た型番の別の商品の資料が返ってきます。文章で症状を尋ねる質問には、正しく答えます。最初に勧める対策はどれでしょうか。1番、より大きなモデルに替える。2番、意味で探す検索に、キーワードの検索を組み合わせる。3番、チャンクを大きくして、1件あたりの情報を増やす。

@pause 4

正解は、2番です。型番のような文字どおりの一致は、意味で探す検索が取りこぼしやすいからです。モデルを大きくしても、渡すチャンクが違えば答えは直りません。
