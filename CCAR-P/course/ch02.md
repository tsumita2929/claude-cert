# 第2章 モデルとプロンプトの設計

- 試験: CCAR-P ／ 分野2 Claude モデル、プロンプト作成、コンテキストエンジニアリング（13%）／ タスク 2.1〜2.5（番号は教材での便宜上のもの）
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第2章は、分野2の、Claude モデル、プロンプト作成、コンテキストエンジニアリングです。配点は13%です。タスクは5つで、モデルの選び方から、プロンプトとコンテキストの設計、そして再利用までを扱います。それぞれの場面で、どの手を、なぜ選ぶのかを見ていきます。

**要点**
- 分野2は配点13%、タスクは5つ
- モデル、プロンプト、コンテキスト、再利用を扱う
- 「どの手を、なぜ選ぶか」を説明できるようにする

### モデルは評価で選び、替える前にも評価を通す

最初のタスクは、トレードオフに基づくモデルの選択です。比べる軸は、品質、速度、コストです。2026年11月時点では、Haiku が最も速く、最も安い系統です。

公式のドキュメントは、始め方を2つ挙げています。速くて安いモデルから始めて、足りないときだけ上げる方法。高性能なモデルから始めて、あとで効率のよいモデルに移す方法です。どちらでも、決め手は、実際のプロンプトとデータを使った評価です。

避けたいのは、評価なしのモデル変更です。適合を見ずに最小のモデルへ替えると、品質を損なうおそれがあります。大きなモデルに替えても、原因が権限や検索にあれば効きません。モデルを替える前には、評価を関門にします。なお、2026年11月時点のドキュメントは、同じモデルのまま考える深さを変える、`effort` の調整も勧めています。

**要点**
- 比べる軸は品質、速度、コスト
- 安いモデルから上げるか、強いモデルから下げるか
- どちらでも、実際のデータでの評価が決め手
- 評価なしの小型化も大型化も誤答の定番

### システムプロンプトには、役割と、変わらない指示と、ガードレールを書く

2つ目のタスクは、システムプロンプト、テンプレート、ガードレールの設計です。システムプロンプトで役割を与えると、1文でも、Claude の振る舞いと口調が用途に合ってきます。指示には理由を添えます。Claude は理由から一般化できるからです。

テンプレートは、毎回変わらない指示と、毎回入れ替わる入力を分けた、ひな形です。入れ替わる部分は XML のタグで囲み、指示と区別します。

ガードレールは、望まない出力や動作を防ぐ仕組みです。情報が足りないときは分からないと答えてよい、と明示すると、誤った情報が大きく減ります。外部の文書やツールの結果は、信頼できないデータとして扱うよう指示します。ただし、プロンプトだけでは完全には防げません。権限を絞る統制と組み合わせます。詳しくは第6章で扱います。

**要点**
- 役割は1文でも効く。指示には理由を添える
- テンプレートは、固定の指示と可変の入力を分ける
- 可変の入力はタグで囲んで区別する
- 「分からない」と答えてよいと明示する
- プロンプトだけに頼らず、権限の統制と組み合わせる

### 手法は、課題の性質で選ぶ

3つ目のタスクは、ゼロショット、few-shot、思考の連鎖の使い分けです。ゼロショットは、例を見せず、指示だけで頼む方法です。まずこれで試し、評価で足りない点が見えたら、手を足します。

few-shot は、入力と出力の例を見せる方法です。形式や口調をそろえる、最も確実な手の1つです。公式のドキュメントは、3つから5つの例を勧めています。例は、用途に近く、互いに違うものを選びます。似た例ばかりだと、意図しない癖まで真似されるからです。

思考の連鎖は、答える前に、段階を追って考えさせる方法です。複雑な推論で役立ちますが、トークンと待ち時間が増えます。2026年11月時点の新しいモデルでは、思考の機能に任せ、考える量を Claude が自分で決めるのが基本です。推論を文章で書き出させるプロンプトは、思考の機能を使えないときの代わりです。

**要点**
- ゼロショットは指示だけ。まずここから試す
- few-shot は形式と口調をそろえる確実な手
- 例は3〜5個。用途に近く、互いに違うもの
- 思考の連鎖は精度と引き換えに時間とトークンを使う
- 新しいモデルでは思考の機能に任せるのが基本

### コンテキストは、量より信号の濃さで管理する

4つ目のタスクは、コンテキストウィンドウの最適化と、トークンの管理です。コンテキストウィンドウは、モデルが応答を作るときに参照できる、作業用の記憶です。システムプロンプト、履歴、ツールの結果、そして出力も、すべてここに数えられます。

ただし、多ければよいわけではありません。トークンが増えるほど、正確に思い出す力が落ちます。これを context rot と呼びます。目指すのは、必要で信号の濃いトークンを、できるだけ少なく渡すことです。

長い文書は上に、質問は最後に置きます。長い会話では、古いツールの結果を消したり、やり取りを要約したりします。送る前には、トークン数を見積もります。逆に、必要な方針文書を切り詰めるのは、誤答の定番です。答えに要る情報まで消えるからです。

**要点**
- 出力も含め、すべてがコンテキストに数えられる
- 増やすほど、思い出す精度は落ちる
- 必要で濃い情報を、できるだけ少なく渡す
- 長い文書は上に、質問は最後に
- 必要な文書の切り詰めは誤答の定番

### 繰り返す部分は、キャッシュとモジュールと Skills で再利用する

5つ目のタスクは、プロンプトの再利用です。手段は3つあります。

1つ目は、プロンプトキャッシングです。キャッシュは、プロンプトの先頭から一致する部分に効きます。ですから、変わらないシステムプロンプトや参照文書を前に、変わる入力を後ろに置きます。繰り返す部分の処理を省けるので、最初のトークンが返るまでの時間と、1回あたりのコストが、両方下がります。情報を捨てない点が、切り詰めとの違いです。先頭に現在時刻などを入れると、毎回キャッシュが外れます。

2つ目は、モジュール型のプロンプトです。役割、方針、出力の形式といった部品に分けて、使い回します。部品の並び順を固定しておけば、キャッシュとの相性もよくなります。

3つ目は、Skills です。指示や手順、スクリプトをまとめた、再利用できる部品です。ふだんは名前と説明だけがコンテキストに載り、課題に合ったときだけ、中身が読み込まれます。毎回すべての指示を詰め込むより、コンテキストを節約できます。この考え方は、第3章の段階的ディスカバリーにつながります。なお、Skills は、信頼できる出どころのものだけを使います。

**要点**
- キャッシュは先頭からの一致で効く
- 固定の部分を前に、変わる入力を後ろに置く
- 待ち時間とコストを、情報を捨てずに下げる
- 部品に分けて並び順を固定し、使い回す
- Skills は必要なときだけ中身が読み込まれる

### ミニクイズ

それでは、ミニクイズです。

ある保険会社が、問い合わせメールの分類を、最上位のモデルで大量に処理しています。コストを下げるため、今すぐ最も安いモデルに替えたい、と相談されました。最も適切な助言はどれでしょうか。1番、すぐに替えて、苦情が出たら元に戻す。2番、実際のメールで評価データセットを作り、安いモデルが基準を満たすと確かめてから替える。3番、モデルはそのままにして、メールの本文を半分に切り詰める。

@pause 4

正解は、2番です。モデルを替える前には、実際のデータでの評価を関門にします。1番は品質の低下に気づくのが遅れ、3番は分類に必要な情報を捨ててしまいます。

### 試験ガイドと現行ドキュメントの食い違い

- 思考の連鎖: 試験ガイド（タスク 2.3）は、ゼロショット、few-shot と並ぶプロンプトの手法として「思考の連鎖」を挙げる。2026年11月時点のドキュメント（Prompting best practices）は、新しいモデルでは adaptive thinking が基本で、推論を書き出させる手作業の CoT プロンプトは「thinking が off のときの fallback」としている。さらに Fable 5 系、Opus 5.5、Opus 5、Sonnet 5.5 では、推論を `<thinking>` タグなどに書き出させるプロンプトは断られることがあり、思考の機能（必要なら低い effort）に任せるよう勧めている。本文はガイドの立場で手法として説明し、現行の扱いを一言添えた。
- モデル選択の手段: 試験ガイドはモデルの選択だけを挙げる。現行のドキュメントは、同じモデルのまま `effort` を調整することを「モデルを替えるより、しばしばよいレバー」としている。本文では一言添えるにとどめた（effort はガイドに名前がない）。
- テンプレート: 試験ガイドはタスク 2.2 で「テンプレート」を挙げるが、現行のドキュメントには、以前あったプロンプトテンプレートと変数の専用ページがない（旧 URL は Prompting best practices に転送される）。本文では、固定の指示と可変の入力を分け、可変の部分をタグで囲むという、best practices とガードレールの各ページの例に沿った説明にした。
