# 第5章 評価・テスト・最適化

- 試験: CCAR-P ／ 分野4 評価、テスト、最適化（16%）／ タスク 4.1〜4.6（番号は便宜上のもの）
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第5章は、分野4の、評価、テスト、最適化です。配点は16%です。指標を決める。評価データセットを作る。A/B テストで改善する。問題を診断する。コストと速さを詰める。本番を見張る。この6つです。通して大事なのは、変更の良し悪しを、感想ではなく、先に決めた物差しで判断することです。

**要点**
- 分野4は配点16%、タスクは6つ
- 指標、データセット、A/B テスト、診断、最適化、モニタリング
- 変更の良し悪しは、先に決めた物差しで判断する

### 成功基準は、測れる形で、複数の軸に決める

最初に、成功基準を決めます。何ができたら成功かを、測れる形で書いたものです。「性能が良い」では足りません。「感情の分類が正確」のように、何を測るかまで決めます。

軸は1つでは足りません。試験ガイドは、精度、レイテンシ、コスト、安全性、セキュリティを挙げています。あいまいな安全性も、数字にできます。たとえば、1万回の試行で、有害と判定された出力が0.1%未満、のように書きます。

この基準は、本番のコードを書く前に決めます。基準がないと、何をもって完成とするかを、あとから都合よく決めてしまうからです。

**要点**
- 成功基準は、何を測るかまで具体的に書く
- 精度、レイテンシ、コスト、安全性、セキュリティで決める
- あいまいな安全性も、割合で数字にできる
- 基準は、本番のコードを書く前に決める

### 評価データセットは本番に似せ、採点の方法を組み合わせる

評価データセットは、本番で実際に来る入力に似せます。そこに、極端に長い入力や、人でも判断が割れる入力のような、まれで難しいケースを加えます。少数を手作業で採点するより、自動で採点できる問題を数多く用意するほうがよい、とドキュメントは言います。最初は、実際の失敗から取った20件から50件でも、良い出発点になります。

採点の方法は3つあり、組み合わせて使います。コードによる採点は、速く、安く、毎回同じ結果になります。ただし、表現が違うだけの正しい答えを、誤りにしがちです。モデルによる採点は、柔軟で、細かな質も見られます。ただし結果が揺れるので、明確な採点基準を与え、人の採点と突き合わせてから広げます。人による評価は、最も質が高い一方で、遅く、費用がかかります。

**要点**
- データセットは本番の入力に似せ、難しいケースを足す
- 少数の手作業より、自動で採点できる多数のケース
- コードは速く確実、モデルは柔軟、人は最も質が高い
- モデルの採点は、人の採点と突き合わせてから広げる

### A/B テストは、仮説と指標を先に決め、結果を言いすぎない

A/B テストは、今の版と新しい版に利用者を振り分けて、本番で比べる方法です。十分な利用量があるときに、大きな変更を確かめるのに使います。

始める前に、仮説と、主に見る指標と、必要な件数を決めます。Claude の出力は、同じ入力でも毎回少し変わります。少ない件数での小さな差は、たまたまかもしれません。1つの指標が良くなっても、コストや安全性が悪くなっていれば、良い変更とは言えません。結果は、言いすぎずに読みます。

本番で見つかった失敗は、評価データセットに足します。こうして、直した問題の再発を変更のたびに確かめる、回帰テストが育ちます。

**要点**
- A/B テストは、本番で今の版と新しい版を比べる
- 仮説、主な指標、必要な件数を先に決める
- 小さな差や1つの指標の改善を、言いすぎない
- 本番の失敗は、評価データセットに足す

### 診断は、何が変わり、何が変わっていないかから始める

診断では、まず、何が変わり、何が変わっていないかを見ます。原因は、その変化とつながるものを選びます。

試験ガイドは、プロンプトの失敗、ハルシネーション、モデルの不適合を挙げています。プロンプトの失敗は、指示があいまいで、形式や範囲がずれるものです。プロンプトを直し、評価データセットで確かめます。

ハルシネーションは、根拠のない内容を、もっともらしく答えるものです。RAG の場合、文書の更新直後に誤答が増え、モデルもレイテンシも変わっていないなら、まず検索とインデックスの段を疑います。プロンプトでは、分からなければ分からないと答えてよいと伝え、根拠の引用を示させます。

モデルの不適合は、能力が足りない、または簡単なタスクに大きすぎて遅く高い、という状態です。同じ評価データセットで、モデルを比べて判断します。

**要点**
- 原因は、変わったことと因果がつながるものを選ぶ
- プロンプトの失敗は、直して評価で確かめる
- RAG のハルシネーションは、まず検索とインデックスを疑う
- モデルの不適合は、同じ評価データセットで比べる

### 最適化は、品質を確かめてから、必要なものを残して行う

最適化は、順番が大切です。まず、よく動くプロンプトを作り、速さとコストはそのあとで詰めます。先に削ると、最高の性能がどこにあるかが分からなくなります。

毎回同じ長い前置きを送るなら、第2章で扱ったプロンプトキャッシングを使います。急ぎでない大量の処理は、Message Batches API に回すと、コストが半分になります。出力は短く頼み、`max_tokens` で上限を決めます。体感の速さには、答えを少しずつ返すストリーミングが効きます。

タスクに合うかを確かめずに、一番小さいモデルにすると、品質を損ないます。簡単な処理は安いモデル、難しい部分だけ能力の高いモデル、という組み合わせもあります。必要な情報を捨てて軽くするのは誤りです。変えたら、同じ評価データセットで確かめます。

**要点**
- まず品質を出し、そのあとで速さとコストを詰める
- 同じ前置きはキャッシュ、急がない大量処理はバッチ
- 出力は短く頼み、上限を決める
- 必要な情報を捨てる最適化は選ばない
- 変えたら、同じ評価データセットで確かめる

### ログは、成功基準と同じ物差しで本番を見張る

最後は、本番のモニタリングです。本番では、入力の傾向が変わったり、想定外の失敗が起きたりします。それを、ログとオブザーバビリティのツールで見つけます。オブザーバビリティとは、外から見える情報で、中の状態をつかめることです。

リクエストごとに、モデル、入力と出力のトークン数、かかった時間、そして `stop_reason` を残します。`stop_reason` は、Claude が出力を止めた理由です。エラーにならずに返っても、`max_tokens` で止まっていれば、答えは途中で切れています。

集めた数字は、成功基準と同じ物差しで見ます。外れたら知らせが届くようにし、失敗は評価データセットに戻します。大規模なモニタリングの戦略は、第4章で扱いました。

**要点**
- 本番の入力の変化と想定外の失敗を、ログで見つける
- モデル、トークン数、時間、`stop_reason` を記録する
- 正常に返っても、`max_tokens` なら途中で切れている
- 成功基準と同じ物差しで見て、外れたら知らせる

### ミニクイズ

それでは、ミニクイズです。

ある小売企業が、コストを下げるため、問い合わせ対応をすべて小さいモデルに切り替えました。評価データセットでは、簡単な問い合わせの正答率は変わらず、返品の条件が絡む複雑な問い合わせだけが、大きく下がりました。最も適切な次の一手はどれでしょうか。1番、すべてを元の大きいモデルに戻す。2番、複雑な問い合わせだけを能力の高いモデルに回し、同じ評価データセットで確かめる。3番、複雑な問い合わせのログを詳しく取り、様子を見る。

@pause 4

正解は、2番です。下がったのは複雑な問い合わせだけなので、その部分でのモデルの不適合です。すべて戻せばコストの削減まで失い、ログを足すだけでは原因が残ります。

### 試験ガイドと現行ドキュメントの食い違い

- 内容の食い違いはなし。試験ガイドの分野4はタスクを1行ずつ挙げるだけで、製品の名前や数値を書いていないため。
- 補足（名前の変化）: 組織の使用量とコストを取る API は、2026年11月時点のドキュメントで「Usage and Cost Analytics API」（ベータ。`anthropic-beta: analytics-usage-cost-2026-08-24`）になっており、以前の「Usage and Cost API」は legacy と表示されている。ガイドの発効（2026年7月）より後の変更と見られる。本文では分量の都合で、組織単位の使用量とコストの集計（Claude Console の Usage と Cost の画面、この API）には触れていない。スライド・動画・問題集で扱うなら、API の固有名を正解の根拠にしないほうが安全。
