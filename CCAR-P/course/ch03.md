# 第3章 統合の設計と認証・認可

- 試験: CCAR-P ／ 分野3 統合（19%）／ タスク 3.1、3.2、3.7、3.8（番号は教材の便宜上のもの。公式のガイドに番号はない）

## 本文

### この章で学ぶこと

第3章は、分野3の「統合」の前半です。分野3の配点は19%で、7つの分野の中で最大です。この章では、機能の肥大化、認証と認可、統合の手段の選び方、そして段階的ディスカバリーの4つを扱います。RAG と運用の見える化は、第4章で扱います。

**要点**
- 分野3「統合」は配点19%で最大
- この章はタスク4つ: 肥大化、認証と認可、統合手段、段階的ディスカバリー
- RAG と運用の見える化は第4章

### 要らない機能は、構成から外す

エージェントに渡すツールや権限が、業務に必要な範囲より広がった状態を、機能の肥大化と言います。判断の軸は、最小権限の原則です。役割に必要のない機能は、構成から取り除きます。たとえば、問い合わせを要約するだけのエージェントに、顧客データを書き換えるツールが付いていたら、外します。

もっともらしい誤答は3つです。ログを足すのは、後から不正を見つける発見的な統制です。実行の前に確認を挟むのは、補完的な統制です。どちらも、危ない機能は残ったままです。大きなモデルに替えるのも筋違いです。モデルの大きさは、認可の範囲と関係がありません。

肥大化は、精度の問題でもあります。ツールが多すぎたり、役割が重なったりすると、エージェントは迷いやすくなります。2026年11月時点のドキュメントでは、ツールが30から50を超えると、選択の精度が落ちるとされています。

**要点**
- 業務に要らないツールと権限は、構成から外す
- ログや確認の追加は、権限を減らさない
- モデルの大きさは、認可の範囲と無関係
- ツールが多すぎると、選択の精度も落ちる

### 認証と認可を分けて、すき間を探す

認証は、相手が誰かを確かめることです。認可は、その相手に何を許すかを決めることです。この2つを分けて、すき間を探します。

まず、MCP の認可は、仕様の上では任意です。つないだだけで守られるわけではありません。ネットワーク越しの HTTP のサーバーは、OAuth 2.1 をもとにした認可の仕様に沿います。手元で起動する STDIO のサーバーは、資格情報を環境から受け取り、クライアントと同じ権限で動きます。そのため、どの資格情報と権限を受け継いでいるかを確かめます。

次に、トークンです。MCP サーバーは、自分あてに発行されたトークンだけを受け付けます。受け取ったトークンを、そのまま先のサービスへ渡すことは、仕様で禁止されています。許可の範囲、つまりスコープも、最初は最小にして、必要なときに広げます。

人と仕組みも分けて考えます。社員の入口は、組織の ID 基盤と SSO でつなぎます。サーバーどうしの通信では、使い回す API キーより、短い期間だけ有効な資格情報を使い、漏れたときの被害を小さくします。

**要点**
- 認証は誰か、認可は何を許すか
- MCP の認可は任意。つないだだけでは守られない
- STDIO のサーバーが受け継ぐ資格情報を監査する
- 受け取ったトークンを先へそのまま渡さない
- 社員は SSO、仕組みは短期の資格情報

### 統合メカニズムは、つなぐ相手と使い方で選ぶ

外部のシステムとつなぐ方法は、大きく3つあります。MCP、API や CLI、そしてエージェント間の連携です。

MCP は、AI のアプリと外部のシステムをつなぐ、オープンな標準です。一度サーバーを作れば、複数のアプリから使い回せます。同じ社内システムを、いくつものアプリやチームで使うなら、MCP が向いています。

API や CLI は、より直接的な方法です。Claude Code のドキュメントは、相手に CLI があれば、たいていそれがいちばん簡単な入り口だと書いています。自分のアプリだけで使う連携なら、API を呼ぶ自作のツールで足ります。

エージェント間の連携は、別のエージェントに仕事を任せる形です。任された側は、自分のコンテキストで作業し、結果をまとめて返します。独立した調べものを並べて進めるのに向きます。ただし Anthropic の報告では、トークンの消費はチャットの約15倍でした。文脈の共有や、作業どうしの依存が多い仕事には、今のところ向きません。

提供ルートも選びます。Claude は、直接の API のほか、Amazon Bedrock や Google Cloud のようなクラウド経由でも使えます。レイテンシ、コンプライアンス、コストで比べ、必要な機能がそのルートで使えるかを先に確かめます。

**要点**
- 多くのアプリで使い回す接続は MCP
- CLI があればまず CLI。アプリ固有なら自作ツール
- エージェント間は、独立した並列の仕事に向く
- 提供ルートごとに、使える機能を先に確かめる

### 段階的ディスカバリーと一括型は、使う頻度で分ける

一括型コンテキストは、必要になりそうな情報を、最初に全部載せる設計です。段階的ディスカバリーは、最初は目次だけを渡し、必要な分をあとから読み込む設計です。

一括型は単純で、実行中に探す手間がありません。ただし、量が増えるとコンテキストを圧迫し、関係のない情報が判断を鈍らせます。

段階的ディスカバリーの代表が、Skills です。最初は名前と説明だけを読み、作業に合えば `SKILL.md` の本文を、さらに必要なら付属のファイルを読みます。ツールでも同じです。ツール検索ツールを使い、定義に `defer_loading` を付けたツールは、検索されて初めてコンテキストに載ります。

代償もあります。実行中に探すぶん遅くなり、説明文があいまいだと見落とします。ツールが10個に満たず、毎回すべてを使うなら、最初から全部渡すほうが合っています。

実際は組み合わせます。Claude Code は、CLAUDE.md を最初に読み込み、ほかのファイルは必要なときに探します。いつも要る小さな情報は先に、ときどき要る大きな情報は後から。これが判断の軸です。

**要点**
- 一括型は単純だが、量が増えるとコンテキストを圧迫
- Skills は名前と説明だけを先に読む
- `defer_loading` のツールは検索されてから載る
- 探すぶん遅く、説明があいまいだと見落とす
- いつも要る小さな情報は先、時々要る大きな情報は後

### ミニクイズ

それでは、ミニクイズです。

ある病院が、電子カルテの API の前に、MCP サーバーを置きました。このサーバーは、届いたアクセストークンを確かめずに、そのまま電子カルテの API へ渡しています。最も適切な見直しはどれでしょうか。1番、すべてのリクエストをログに残す。2番、自分あてに発行されたトークンだけを受け付け、電子カルテの API には、別に発行されたトークンを使う。3番、指示によく従う、より大きなモデルに替える。

@pause 4

正解は、2番です。受け取ったトークンをそのまま先へ渡すことは、MCP の仕様で禁止されています。ログは後から見つけるための統制で、すき間は残ります。

### 試験ガイドと現行ドキュメントの食い違い

- 提供ルートの名前: 試験ガイド v1.0 は提供ルートに触れず、公式の対策講座（講座4）は「Bedrock、Vertex」と書く。2026年11月時点の Anthropic のドキュメントでは、Google Cloud 経由の提供は「Claude Models on Google Cloud」と呼ばれ、Anthropic が運用するものと Google が運用するもの（Google Cloud の Agent Platform。旧称 Vertex AI。https://code.claude.com/docs/en/google-vertex-ai の説明「Google Cloud's Agent Platform, formerly Vertex AI」）の2つがある。Amazon Bedrock にも bedrock-runtime と bedrock-mantle の2つの入口があり、ほかに Claude Platform on AWS と Microsoft Foundry がある。本文では、細部に踏み込まないよう「Amazon Bedrock や Google Cloud のようなクラウド経由」とだけ書き、Vertex AI の名前は出さなかった。問題集で Vertex AI の名前を使う場合は、旧称であることを解説に添えるとよい。
- MCP の仕様の版: 試験ガイドは MCP の版を指定していない。本文の認可の記述は、2026年11月時点で確認できた仕様 2025-11-25 版（authorization と security best practices）に基づく。「認可は任意」「HTTP は OAuth 2.1 ベースの仕様に沿う」「STDIO は環境から資格情報を取る」「トークンパススルーの禁止」は、この版で確認した。新しい版で表現が変わる可能性がある。
