# 第8章 開発チームの生産性と運用

- 試験: CCAR-P ／ 分野7 開発者の生産性と運用支援（7%）／ タスク 7.1〜7.3
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第8章は、分野7の、開発者の生産性と運用支援です。配点は7%で、いちばん小さい分野です。タスクは3つです。チーム向けに Claude のツールと環境を構成すること。AI 支援ツールで開発者のワークフローを改善すること。そして、デバッグと運用上の問題解決を支援することです。題材は、試験ガイドが例に挙げる Claude Code です。

**要点**
- 分野7は配点7%で、いちばん小さい分野
- タスクは、環境の構成、ワークフローの改善、問題解決の支援の3つ
- 題材は、試験ガイドが例に挙げる Claude Code

### チームの設定は共有し、守らせたい方針は管理設定で配る

Claude Code の設定には、効く範囲の違う置き場所があります。ホームディレクトリのユーザー設定は、自分だけに効きます。リポジトリにコミットする `.claude/settings.json` は、チーム全員に効きます。そして、組織が配る管理設定、英語では managed settings があります。

管理設定は、いちばん優先され、開発者は上書きできません。許可や拒否のルールの一覧は、すべての置き場所の分が合わさります。開発者はルールを足せても、組織のルールは外せません。

配り方は2つです。1つは、claude.ai の管理コンソールから配る、サーバー管理の設定です。もう1つは、MDM、つまり端末を一括で管理する仕組みや、決まった場所のファイルで配る方法です。ただし、サーバー管理の設定は端末の側で効く仕組みで、セキュリティの境界ではない、とドキュメントは書いています。強く守らせたいなら、MDM で管理する端末に配ります。配ったあとは、`/status` で、組織の設定が効いているかを確かめます。

**要点**
- チームの設定は、リポジトリにコミットして共有する
- 管理設定は最優先で、開発者は上書きできない
- 許可や拒否の一覧は合わさり、足せても外せない
- サーバー管理の設定は、セキュリティの境界ではない
- 配ったら `/status` で効いているかを確かめる

### 手順はスキルにまとめ、届けたい範囲で配り方を選ぶ

チームのリリース手順や障害対応の手順書は、スキルにまとめます。スキルは、ふだんは名前と説明だけがコンテキストに入り、必要なときに本文が読まれます。同じ内容を CLAUDE.md に長く書くより、ほかの作業の邪魔をしません。

配り方は、届けたい範囲で選びます。1つのリポジトリなら、`.claude/skills` にコミットします。広く配るなら、プラグインにまとめ、マーケットプレイス、つまりプラグインの目録から配ります。組織全体には管理設定を使い、指定したプラグインを全員の端末で有効にできます。開発者が追加できるマーケットプレイスを、承認したものだけに制限することもできます。担当者のホームディレクトリに置くだけでは、チームに届きません。

**要点**
- チームの手順や知識は、スキルにまとめる
- スキルの本文は、必要なときだけ読み込まれる
- リポジトリならコミット、広く配るならプラグイン
- 管理設定で、プラグインの配布と入手先の制限ができる
- 個人のホームディレクトリでは、チームに届かない

### 支出の管理も、チームの設定に含める

支出の管理は、見える化と上限の2つで考えます。Team と Enterprise のプランでは、席ごとの利用枠を超えた分に、組織、グループ、メンバーの単位で上限を決められます。分析のダッシュボードでは、利用者の数のような定着の度合いが見え、メンバーごとの支出はレポートで確かめます。どの提供ルートでも、OpenTelemetry で、利用のデータを自社のモニタリングの仕組みへ送れます。

**要点**
- 支出の管理は、見える化と上限の両方で考える
- 組織、グループ、メンバーの単位で上限を決められる
- 定着はダッシュボード、支出はレポートで見る
- OpenTelemetry で、自社のモニタリングの仕組みへ送れる

### AI が書いた成果物は、書き手と別の検証を通す

AI 支援ツールでワークフローを改善するときの要は、レビューの規律です。Claude は、作業が終わったように見えたところで止まります。そこで、テストやビルドのように、合格か不合格かを返す確かめ方を渡します。完了の報告には、実行したコマンドと出力という証拠を求めます。「テストは通りました」という要約だけを信じてはいけません。

レビューは、書いた本人ではない目で行います。Claude Code の `/code-review` は、会話を見ていない新しいサブエージェントで差分を確かめるので、コードを生んだ推論に引きずられません。

もう1つの軸は、ルールの置き場所です。CLAUDE.md やスキルは、モデルが読んで判断する指示なので、守られないことがあります。毎回必ず守らせたいことは、フック、拒否のルール、管理設定のように、Claude Code が強制する仕組みに置きます。最後の決定は、ブランチの保護と、マージを承認する人に残します。

**要点**
- 合格か不合格かを返す確かめ方を渡す
- 完了の報告には、コマンドと出力という証拠を求める
- レビューは、書いた本人ではない目で行う
- 必ず守らせたいことは、強制する仕組みに置く
- 最後の決定は、ブランチの保護と承認する人に残す

### 症状を、原因のある層に結びつける

デバッグと運用上の問題解決では、症状を、その原因がある層に結びつけます。たとえば、リポジトリに入れた設定が、ある開発者にだけ効かないとします。まず `/status` で、どの設定が読み込まれているかを見ます。上の層が、同じ項目を決めているのかもしれません。許可のルールのように、その人がフォルダーを信頼するまで効かない項目もあります。CLAUDE.md のルールがときどき破られるなら、言葉を強めても直りません。モデルが判断する層に置いたことが原因なので、強制する仕組みへ移します。

コードの不具合を調べるときは、再現の手順とエラーの全文を渡し、毎回起きるのか、ときどきなのかも伝えます。よくある問題の切り分け方はスキルにまとめ、チームが自分たちで解決できるようにします。

この講座のどの章でも、判断の軸は同じです。原因を取り除く対応を選び、必要なものは捨てず、必ず守らせたいことは仕組みで強制します。

**要点**
- 症状を、原因のある層に結びつけて切り分ける
- 設定が効かないときは、まず `/status` で読み込み元を見る
- ときどき破られるルールは、強制する仕組みへ移す
- よく起きる問題の切り分け方は、スキルにして共有する

### ミニクイズ

それでは、ミニクイズです。

ある金融機関では、「環境変数のファイルを読まない」というルールを CLAUDE.md に書いていますが、ときどき破られます。全開発者に確実に守らせるには、どれが最も適切でしょうか。1番、CLAUDE.md の文に「絶対に」と書き足す。2番、ファイルを読んだ記録を集め、違反をあとで見つける。3番、拒否のルールを管理設定に入れて配る。

@pause 4

正解は、3番です。管理設定の拒否のルールは、Claude Code が毎回強制し、開発者は外せません。1番はモデルの判断に任せたままで、2番はあとで見つける統制なので、違反そのものは防げません。

### 試験ガイドと現行ドキュメントの食い違い

- なし。試験ガイドの分野7は、タスクが1行ずつで、Claude Code の具体的な設定名や機能名を挙げていない。そのため、ガイドと現行ドキュメントが直接ぶつかる点はない。本文の機能の説明は、2026年11月時点の Claude Code のドキュメントに基づく。
- 参考: 第三者の対策サイト（blueprint.md 4章 (b)）には「server-managed settings で上書きできないセキュリティ設定を強制する」という趣旨の記述がある。現行ドキュメントは、サーバー管理の設定は端末の側の仕組みで、セキュリティの境界ではないと明記している。本文はドキュメントに従い、「強い保証が要るなら MDM の端末に配る」と添えた。問題集の担当は、サーバー管理の設定を「回避できない」とする正答を作らないこと。
