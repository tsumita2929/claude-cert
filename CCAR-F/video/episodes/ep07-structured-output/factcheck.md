## 画面だけの例示（事実の主張ではないもの）

- **semantic の場面のコード**（`line_items` が 3000 と 5000、`total` が 9000、`shipping_address` に請求先の住所）は、素材の本文の2つの例（明細の合計が合わない、請求先の住所が送付先の項目に入る）を、説明のために JSON の形にした架空のデータ。項目名は説明用で、API やガイドで決まった名前ではない。
- **validate の場面の項目名**（`stated_total`、`calculated_total`、`conflict_detected`）と **retry の場面の `detected_pattern`** は、試験ガイドに出てくる名前（素材 #11、#14）。声では長い英語の名前を読まず、役割を日本語で言っている（音声エンジンが語の途中で区切るため）。

## 試験ガイドと現行ドキュメントの食い違い（素材と同じ立場で扱った）

1. **強制のツール選択（`tool_choice` の `any` と名前の指定）。** ガイドは構造化出力を保証する手段として扱う。2026年11月時点の define-tools のページでは、新しいモデルの一部（Claude Fable 5.2、Mythos 5.2、Opus 5.5、Sonnet 5.5、Fable 5.1、Mythos 5.1）で 400 エラーになり、代わりに `auto` と strict tool use を使う。台本はガイドの立場で3つの違いを教え、「2026年11月時点では、新しいモデルの一部で、この2つの強制が400のエラーになる。その場合は `auto` にして、ツールに `strict: true` を付ける」と一言添えた（素材と同じ）。
2. **スキーマへの準拠を何が保証するか。** ガイドは「JSON スキーマを用いたツール使用」を最も信頼できる方法とする。現行の strict-tool-use のページは、strict モードなしでは型の違い（`"2"` と `2`）や必須項目の欠落がありうるとし、準拠を保証するのは `strict: true` と structured outputs だとしている。台本は「試験ガイドが、最も信頼できる方法とするのが、ツール使用です」と、ガイドの立場であることを明示して書き、現行の手段としては `strict: true` だけを choice の場面で添えた。structured outputs の名前は出していない（素材と同じ）。
3. **バッチでのツール使用。** 現行の batch-processing のページは、バッチにツールの定義（サーバーツールを含む）や過去の会話を入れられるとする。台本は素材と同じく「アプリがツールを実行して、結果を返せない」と書き、「バッチではツールを使えない」とは言い切っていない。
