# CCAR-F 教材の設計（章立てと問題の配分）

Claude Certified Architect – Foundations（試験コード CCAR-F。通称 CCA-F）の非公式教材の設計です。講座（音声・スライド・動画）の章立てと、問題集の配分をここで決めています。出題範囲の詳しい調査は `blueprint.md`、公式の試験ガイドは同じフォルダの PDF とテキストにあります。

## 試験の基本情報（公式試験ガイド v1.0、2026年7月発効。2026-11-16 に確認）

| 項目 | 内容 |
|---|---|
| 問題数・時間 | 60問・120分（受付などを含めた着席時間は約135分） |
| 合格点 | 100〜1,000 のスケールスコアで 720。換算式は非公開（「72%正解」という意味ではない） |
| 出題形式 | 択一式と複数選択式（選ぶ数は問題に書いてある）。**6つのシナリオのうち4つ**が無作為に選ばれ、各シナリオが一連の問題の前提になる |
| 受験 | Pearson VUE。オンライン監督（OnVUE）かテストセンター。クローズドブック。英語と日本語で受験できる |
| 受験資格 | Claude Partner Network に加盟している組織の人（会社のメールアドレスで申し込む）。前提資格はなし |
| 料金・有効期間 | 125 USD（パートナーの割引前）・12か月 |
| 対象者 | Claude で本番アプリを設計・実装するソリューションアーキテクト。Claude API、Agent SDK、Claude Code、MCP での実務6か月以上が目安 |
| 今後の変更 | 2026-12-07 の試験内容の更新（CCAO-F・CCDV-F・CCAR-P が対象）に、CCAR-F は含まれていない |

分野（公式の日本語版ガイドは domain を「分野」と訳す）と配点:

| 分野 | 名称 | 配点 | タスクステートメント |
|---|---|---|---|
| 分野1 | エージェントアーキテクチャとオーケストレーション（Agentic Architecture & Orchestration） | 27% | 1.1〜1.7 |
| 分野2 | ツール設計と MCP 統合（Tool Design & MCP Integration） | 18% | 2.1〜2.5 |
| 分野3 | Claude Code の設定とワークフロー（Claude Code Configuration & Workflows） | 20% | 3.1〜3.6 |
| 分野4 | プロンプトエンジニアリングと構造化出力（Prompt Engineering & Structured Output） | 20% | 4.1〜4.6 |
| 分野5 | コンテキスト管理と信頼性（Context Management & Reliability） | 15% | 5.1〜5.6 |

シナリオ（S1〜S6。`exam.json` の `scenarios` と同じ）: S1 カスタマーサポート解決エージェント（主な分野 1・2・5）／S2 Claude Code によるコード生成（3・5）／S3 マルチエージェントリサーチシステム（1・2・5）／S4 Claude による開発者の生産性向上（2・3・1）／S5 継続的インテグレーションのための Claude Code（3・4）／S6 構造化データ抽出（4・5）。

各章の範囲の補足（タスクステートメントの全文と「知識」「スキル」の箇条書きは、試験ガイドの本文を読むこと）:

1. **エージェントループと制御** — 1.1 エージェントループ（`stop_reason` が `tool_use` の間は続け `end_turn` で終える、ツール結果を履歴に足す、自然文の解析や反復回数の上限だけで終了を決めない）。1.4 多段のワークフローと、プログラムによる強制（前提条件ゲート）とプロンプトでの誘導の使い分け、人への引き継ぎの要約。1.5 Agent SDK のフック（`PostToolUse` でツール結果を正規化、ツール呼び出しを横取りして方針違反を止める）。この章の芯は「必ず守らせたいことは、プロンプトではなく仕組みで強制する」。サブエージェントは第2章、ツールの説明文は第3章。
2. **マルチエージェントの設計** — 1.2 コーディネーターとサブエージェント（ハブアンドスポーク、サブエージェントは文脈を引き継がない、分解が狭すぎると抜けが出る）。1.3 サブエージェントの起動と文脈の渡し方（`Task` ツール、`allowedTools`、必要な文脈をプロンプトに明示、並列の起動）。1.6 タスク分解（決まった手順のプロンプトチェーンと、動的な分解）。1.7 セッションの状態（`--resume`、`fork_session`、古くなった文脈は要約して新しく始める）。エラーの伝え方は第8章（5.3）。
3. **ツール設計と MCP 統合** — 2.1 ツールの説明文と境界。2.2 MCP ツールの構造化されたエラー（`isError`、エラーの種類、再試行できるか）。2.3 ツールの配り方と `tool_choice`（役割に必要なツールだけ、数が多すぎると選択の精度が落ちる）。2.4 MCP サーバーの設定（プロジェクトの `.mcp.json` とユーザー単位、環境変数展開、リソース）。2.5 組み込みツール（Read、Write、Edit、Bash、Grep、Glob）の選び方。
4. **Claude Code の設定** — 3.1 CLAUDE.md の階層（ユーザー、プロジェクト、ディレクトリ）、`@import`、`.claude/rules/`。3.2 カスタムスラッシュコマンドとスキル（`.claude/commands/`、`.claude/skills/`、フロントマターの `context: fork`、`allowed-tools`、`argument-hint`、プロジェクト単位と個人単位）。3.3 パスを指定したルール（YAML フロントマターの `paths` と glob パターン）。
5. **Claude Code の進め方と CI** — 3.4 プランモードと直接実行の使い分け（Explore サブエージェントを含む）。3.5 反復的な改善（入出力の具体例、テスト駆動、インタビューパターン）。3.6 CI/CD への組み込み（`-p`、`--output-format json`、`--json-schema`、CLAUDE.md で CI に文脈を渡す、生成したセッションと別のセッションでレビューする）。
6. **プロンプト設計とレビュー** — 4.1 明示的な基準で精度を上げ、誤検知を減らす（「保守的に」のような曖昧な指示では直らない）。4.2 few-shot（あいまいな場面に絞った例、形式の見本）。4.6 複数インスタンス・複数パスのレビュー（セルフレビューの限界、独立したレビューインスタンス、ファイルごとのパスと横断のパス）。
7. **構造化出力とバッチ処理** — 4.3 `tool_use` と JSON スキーマによる構造化出力（`tool_choice`、必須と任意、nullable、enum と "other"）。4.4 検証・リトライ・フィードバックのループ（スキーマの検証と意味の検証、リトライで直る誤りと直らない誤り）。4.5 バッチ処理（Message Batches API、50%のコスト削減、最大24時間、`custom_id`、待てる処理と待てない処理）。
8. **コンテキスト管理と信頼性** — 5.1 長い対話で大事な情報を保つ（段階的な要約の落とし穴、「ケースの事実情報」ブロック、lost in the middle、ツール出力の削り込み）。5.2 エスカレーションとあいまいさの解消。5.3 マルチエージェントでのエラーの伝え方。5.4 大きなコードベースの探索（スクラッチパッドファイル、サブエージェント、`/compact`）。5.5 人によるレビューと確信度のキャリブレーション（層化無作為抽出）。5.6 情報の出所と不確かさ（主張と情報源の対応付け、食い違いの注記）。6つのタスクを1章で扱うので、1タスク1節でテンポよく。

**試験ガイドは2026年3月の製品を前提にしている**（v1.0 でも出題内容は変わっていない）。その後に変わった点（例: 新しいモデルの一部では `tool_choice` の `any` や特定ツールの強制が 400 エラーになる、機能の名前の変更など）は、`shared/guides/course-guide.md` の決まりどおり、ガイドの立場を主にして、現行の違いを一言添える。
