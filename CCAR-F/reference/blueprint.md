### 1-2. この資格が証明すること・対象者

- 証明すること：Claude で実際のソリューションを実装するときに、**トレードオフを踏まえた判断**ができること。範囲は **Claude Code、Claude Agent SDK、Claude API、Model Context Protocol（MCP）** の基礎知識［公式：ガイド §1］。
- 問題は実際の顧客事例をもとにしたシナリオで出る。概念の知識だけでなく、本番運用でのアーキテクチャ・設定・トレードオフの判断力を見る［公式：ガイド §1］。
- 理想の受験者：Claude で本番アプリを設計・実装する**ソリューションアーキテクト**。次の実務経験を持つ人［公式：ガイド §2］：
  - Claude Agent SDK でのエージェント構築（マルチエージェントのオーケストレーション、サブエージェントへの委任、ツール統合、ライフサイクルフック）
  - チームの開発フロー向けの Claude Code の設定（CLAUDE.md、Agent Skills、MCP サーバー、プランモード）
  - バックエンド連携のための MCP のツールとリソースのインターフェース設計
  - 信頼できる構造化出力を出すプロンプト設計（JSON スキーマ、few-shot、抽出パターン）
  - 長い文書・複数ターンの会話・エージェント間の引き継ぎにまたがるコンテキストウィンドウの管理
  - CI/CD への Claude の組み込み（自動コードレビュー、テスト生成、PR へのフィードバック）
  - エスカレーションと信頼性の判断（エラー処理、人間が関わるワークフロー、自己評価のパターン）
- 想定する経験：Claude API・Agent SDK・Claude Code・MCP を使った構築の**実務経験が通常6か月以上**。本番での LLM の能力と限界の両方を理解している［公式：ガイド §2］。これは目安で、受験の条件ではない。

### Domain 1: Agentic Architecture & Orchestration（27%）

#### 1.1 Design and implement agentic loops for autonomous task execution ［公式］
公式訳：自律的なタスク実行のためのエージェントループを設計し実装する
- K：エージェントループの一周：Claude にリクエストを送る → stop_reason を確認する（"tool_use" か "end_turn" か）→ 要求されたツールを実行する → 結果を返して次の周へ。
- K：ツールの結果が会話履歴に追加され、モデルが次の行動を推論できる仕組み。
- K：モデル主導の判断（次にどのツールを呼ぶかを文脈から Claude が推論する）と、事前に決めた決定木や固定のツール順序との違い。
- S：stop_reason が "tool_use" なら続け、"end_turn" なら終える制御フローを実装する。
- S：周と周のあいだにツールの結果を会話コンテキストへ追加し、新しい情報を推論に取り込ませる。
- S：アンチパターンを避ける：自然言語の合図を解析して終了を判断する、根拠のない反復回数の上限を主な停止手段にする、アシスタントのテキストの有無を完了の目印にする。

#### 1.2 Orchestrate multi-agent systems with coordinator-subagent patterns ［公式］
公式訳：コーディネーター・サブエージェントパターンでマルチエージェントシステムをオーケストレーションする
- K：ハブアンドスポーク型：コーディネーターが、サブエージェント間の通信・エラー処理・情報の振り分けをすべて受け持つ。
- K：サブエージェントは分離されたコンテキストで動き、コーディネーターの会話履歴を自動では引き継がない。
- K：コーディネーターの役割：タスクの分解、委任、結果の集約、問い合わせの複雑さに応じてどのサブエージェントを呼ぶかの判断。
- K：コーディネーターの分解が狭すぎると、幅広い調査テーマの一部しかカバーできなくなるリスク。
- S：毎回パイプライン全体を通すのではなく、問い合わせの要件を分析して呼ぶサブエージェントを動的に選ぶコーディネーターを設計する。
- S：重複を減らすように調査範囲を分ける（例：サブトピックや情報源の種類ごとに別のエージェントに割り当てる）。
- S：反復改善のループ：コーディネーターが統合結果の抜けを評価 → 的を絞った問い合わせで検索・分析のサブエージェントに再委任 → カバーが十分になるまで統合をやり直す。
- S：観測しやすさ、エラー処理の一貫性、情報の流れの制御のために、サブエージェントの通信をすべてコーディネーター経由にする。

#### 1.3 Configure subagent invocation, context passing, and spawning ［公式］
公式訳：サブエージェントの呼び出し、コンテキストの受け渡し、生成を設定する
- K：サブエージェントを起動する仕組みとしての **Task ツール**。コーディネーターがサブエージェントを呼ぶには、**allowedTools に "Task"** を含める必要がある。
- K：サブエージェントの文脈はプロンプトで明示的に渡す必要がある。親の文脈を自動では引き継がず、呼び出しをまたいでメモリも共有しない。
- K：**AgentDefinition** の設定：サブエージェントの種類ごとの説明、システムプロンプト、ツールの制限。
- K：共通の分析結果を起点に、別のアプローチを探るためのフォーク型のセッション管理。
- S：前のエージェントの調査結果を丸ごとサブエージェントのプロンプトに入れる（例：Web 検索の結果と文書分析の出力を統合役に渡す）。
- S：エージェント間で文脈を渡すとき、構造化データで本文とメタデータ（出典 URL、文書名、ページ番号）を分け、出典の帰属を保つ。
- S：コーディネーターの**1回の応答で複数の Task 呼び出し**を出して、サブエージェントを並列に起動する（ターンを分けない）。
- S：手順を一つずつ指示するのではなく、**調査の目標と品質基準**を示すコーディネーター用のプロンプトを書き、サブエージェントが状況に合わせて動けるようにする。

#### 1.4 Implement multi-step workflows with enforcement and handoff patterns ［公式］
公式訳：強制とハンドオフのパターンを用いて複数ステップのワークフローを実装する
- K：処理の順序を守らせる方法として、プログラムによる強制（フック、前提条件ゲート）とプロンプトによる誘導の違い。
- K：決定論的に守らせる必要がある場面（例：お金に関わる操作の前の本人確認）では、プロンプトの指示だけでは失敗率がゼロにならない。
- K：途中でエスカレーションするための構造化された引き継ぎ手順（顧客の情報、根本原因の分析、推奨する対応を含む）。
- S：前のステップが終わるまで後ろのツール呼び出しを止める、プログラムによる前提条件を実装する（例：get_customer が確認済みの顧客 ID を返すまで process_refund を止める）。
- S：用件が複数ある依頼を個別の項目に分け、共有の文脈を使ってそれぞれを並行して調べ、ひとつの解決策にまとめる。
- S：会話の記録を見られない人間の担当者に回すときに、構造化した引き継ぎ要約（顧客 ID、根本原因、返金額、推奨する対応）を作る。

#### 1.5 Apply Agent SDK hooks for tool call interception and data normalization ［公式］
公式訳：ツール呼び出しのインターセプトとデータ正規化のためにAgent SDKのフックを適用する
- K：モデルが処理する前にツールの結果を横取りして変換するフックのパターン（例：**PostToolUse**）。
- K：送り出されるツール呼び出しを横取りして、規則を守らせるフックのパターン（例：しきい値を超える返金を止める）。
- K：フックによる決定論的な保証と、プロンプトの指示に頼る確率的な遵守との違い。
- S：PostToolUse フックで、MCP ツールごとにばらばらなデータ形式（Unix タイムスタンプ、ISO 8601、数値のステータスコード）を、エージェントが処理する前にそろえる。
- S：方針に反する操作（例：$500 を超える返金）を止め、別のワークフロー（例：人間へのエスカレーション）に回す、ツール呼び出しの横取り用フックを実装する。
- S：業務ルールを確実に守らせる必要があるときは、プロンプトではなくフックを選ぶ。

#### 1.6 Design task decomposition strategies for complex workflows ［公式］
公式訳：複雑なワークフローのためのタスク分解戦略を設計する
- K：固定の順番どおりのパイプライン（プロンプトチェーン）と、途中で分かったことに応じて組み替える動的な分解を、どう使い分けるか。
- K：レビューを順番のステップに分けるプロンプトチェーンのパターン（例：まずファイルを1つずつ分析し、次にファイルをまたぐ統合のパスを回す）。
- K：各ステップで見つかったことからサブタスクを作る、適応的な調査計画の価値。
- S：ワークフローに合う分解の型を選ぶ。予測できる多観点のレビューにはプロンプトチェーン、終わりの見えない調査には動的な分解。
- S：大きなコードレビューを、ファイルごとのローカル分析パスと、別に回すファイル横断の統合パスに分け、注意の分散を避ける。
- S：終わりの見えないタスク（例：「レガシーなコードベースに網羅的なテストを足す」）を、構造の把握 → 影響の大きい領域の特定 → 依存関係が見つかるたびに変わる優先順位付きの計画、という順で分解する。

#### 1.7 Manage session state, resumption, and forking ［公式］
公式訳：セッションの状態、再開、フォークを管理する
- K：**--resume <session-name>** で、名前を付けた過去の会話を再開する。
- K：**fork_session** で、共通の分析結果から独立した分岐を作り、別のアプローチを探る。
- K：コードを変えたあとに再開するとき、分析済みのファイルが変わったことをエージェントに伝える大切さ。
- K：古いツールの結果を抱えたまま再開するより、構造化した要約を持って新しいセッションを始めるほうが確実な理由。
- S：セッション名を付けた --resume で、作業日をまたいで調査を続ける。
- S：fork_session で並行の探索の分岐を作る（例：同じコードベース分析から、2つのテスト戦略やリファクタリング案を比べる）。
- S：再開する（前の文脈がおおむね有効なとき）か、要約を入れて新しく始める（前のツールの結果が古いとき）かを選ぶ。
- S：再開したセッションに具体的なファイルの変更を伝え、全体を探し直させずに、的を絞って分析し直させる。

### Domain 2: Tool Design & MCP Integration（18%）

#### 2.1 Design effective tool interfaces with clear descriptions and boundaries ［公式］
公式訳：明確な説明と境界を備えた効果的なツールインターフェースを設計する
- K：LLM がツールを選ぶ主な手がかりは**ツールの説明（description）**。説明が短すぎると、似たツールのあいだで選択が不安定になる。
- K：説明に、入力の形式、問い合わせの例、エッジケース、担当範囲の境界を書く大切さ。
- K：あいまいな説明や重なり合う説明が、呼び先の取り違えを生む（例：ほとんど同じ説明の analyze_content と analyze_document）。
- K：システムプロンプトの言い回しがツール選択に影響する。特定のキーワードに反応する指示が、意図しないツールとの結び付きを作ることがある。
- S：各ツールの目的、入力、出力、似たツールではなくそれを使うべき場面を、はっきり区別できる説明を書く。
- S：機能の重なりをなくすために、ツールの名前を変えて説明を書き直す（例：analyze_content を extract_web_results に改名し、Web 専用の説明にする）。
- S：汎用のツールを、入出力の約束が決まった目的別のツールに分ける（例：analyze_document を extract_data_points・summarize_content・verify_claim_against_source に分ける）。
- S：よく書けたツールの説明を打ち消してしまう、キーワードに反応する指示がないか、システムプロンプトを見直す。

#### 2.2 Implement structured error responses for MCP tools ［公式］
公式訳：MCPツールの構造化されたエラーレスポンスを実装する
- K：ツールの失敗をエージェントに伝える、MCP の **isError フラグ**のパターン。
- K：一時的なエラー（タイムアウト、サービスの停止）、検証エラー（不正な入力）、ビジネスエラー（方針違反）、権限エラーの区別。
- K：一律のエラー（汎用の「Operation failed」）を返すと、エージェントが適切な立て直し方を判断できない理由。
- K：リトライしてよいエラーとだめなエラーの違い。構造化したメタデータを返せば無駄なリトライを防げる。
- S：errorCategory（transient／validation／permission）、isRetryable（真偽値）、人が読める説明を含む、構造化したエラー情報を返す。
- S：業務ルール違反には「retriable: false」と、顧客に分かりやすい説明を付け、エージェントが適切に伝えられるようにする。
- S：一時的な失敗はサブエージェントの中で立て直し、そこで解決できないエラーだけを、途中までの結果と試したこととあわせてコーディネーターに上げる。
- S：アクセスの失敗（リトライするか判断が要る）と、有効な空の結果（正常に検索できたが該当がない）を区別する。
- メモ：ガイドの中で **isRetryable と retriable の表記が混ざっている**。綴りで正誤が決まる問題は作らないほうが安全［筆者の見立て］。

#### 2.3 Distribute tools appropriately across agents and configure tool choice ［公式］
公式訳：エージェント間でツールを適切に配分し、ツール選択を設定する
- K：エージェントに持たせるツールが多すぎる（例：4〜5個ではなく18個）と、判断が複雑になり、選択の信頼性が下がるという原則。
- K：専門外のツールを持ったエージェントは誤用しがち（例：統合役のエージェントが Web 検索を試みる）。
- K：ツールの範囲を絞る：役割に必要なものだけを渡し、頻繁に必要になる特定の用途だけ、役割をまたぐツールを限定して渡す。
- K：**tool_choice** の選択肢："auto"、"any"、特定のツールの強制（{"type": "tool", "name": "..."}）。
- S：サブエージェントごとに、役割に関係するツールだけに絞り、専門外の誤用を防ぐ。
- S：汎用のツールを、制約付きの代わりのツールに置き換える（例：fetch_url を、文書の URL を検証する load_document に置き換える）。
- S：頻繁に必要になる用途には範囲を絞った役割横断のツールを渡し（例：統合役に verify_fact）、複雑なケースはコーディネーター経由のままにする。
- S：tool_choice の強制で特定のツールを最初に呼ばせ（例：情報を付け足すツールより先に extract_metadata）、その後の処理は次のターンで行う。
- S：tool_choice: "any" にして、会話のテキストではなく必ずツールを呼ばせる。

#### 2.4 Integrate MCP servers into Claude Code and agent workflows ［公式］
公式訳：MCPサーバーをClaude Codeとエージェントワークフローに統合する
- K：MCP サーバーの適用範囲：チームで共有するものはプロジェクト単位（**.mcp.json**）、個人用・試験用はユーザー単位（**~/.claude.json**）。
- K：.mcp.json の**環境変数展開**（例：${GITHUB_TOKEN}）で、秘密情報をコミットせずに認証情報を扱う。
- K：設定したすべての MCP サーバーのツールは接続時に見つけられ、エージェントから同時に使える。
- K：**MCP リソース**でコンテンツの目録（例：課題の要約、ドキュメントの階層、データベースのスキーマ）を見せ、手探りのツール呼び出しを減らす。
- S：共有の MCP サーバーをプロジェクトの .mcp.json に設定し、認証トークンは環境変数展開で渡す。
- S：個人用・試験用のサーバーをユーザーの ~/.claude.json に設定する。
- S：MCP ツールの説明に機能と出力を詳しく書き、エージェントがより高機能な MCP ツールではなく組み込みツール（Grep など）を選んでしまうのを防ぐ。
- S：一般的な連携（例：Jira）には自作より既存のコミュニティ製 MCP サーバーを選び、自作はチーム固有のワークフローに限る。
- S：コンテンツの目録を MCP リソースとして公開し、手探りの呼び出しなしで、どんなデータがあるかをエージェントに見せる。

#### 2.5 Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively ［公式］
公式訳：組み込みツール（Read、Write、Edit、Bash、Grep、Glob）を効果的に選択し適用する
- K：**Grep** はファイルの中身の検索（関数名、エラーメッセージ、import 文などのパターン）。
- K：**Glob** はファイルパスのパターン一致（名前や拡張子でファイルを探す）。
- K：**Read／Write** はファイル全体の操作、**Edit** は一意に一致するテキストを手がかりにした部分修正。
- K：一致する箇所が一意でなく Edit が失敗したら、Read＋Write を確実な代わりの手段にする。
- S：コードの中身を探すには Grep を選ぶ（例：ある関数の呼び出し元をすべて探す、エラーメッセージの場所を探す）。
- S：命名パターンでファイルを探すには Glob を選ぶ（例：**/*.test.tsx）。
- S：Edit が一意の目印を見つけられないときは、Read でファイル全体を読み込んでから Write で書く。
- S：最初に全部のファイルを読むのではなく、Grep で入口を見つけ、Read で import をたどって処理の流れを追う、という順で少しずつ理解する。
- S：ラッパーのモジュールを経由した関数の使われ方を追うときは、まずエクスポートされた名前をすべて洗い出し、それぞれをコードベース全体で検索する。

### Domain 3: Claude Code Configuration & Workflows（20%）

#### 3.1 Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization ［公式］
公式訳：適切な階層、スコープ設定、モジュール構成でCLAUDE.mdファイルを設定する
- K：CLAUDE.md の階層：ユーザー単位（~/.claude/CLAUDE.md）、プロジェクト単位（.claude/CLAUDE.md またはルートの CLAUDE.md）、ディレクトリ単位（サブディレクトリの CLAUDE.md）。
- K：ユーザー単位の設定はその人だけに効く。~/.claude/CLAUDE.md の指示はバージョン管理でチームに共有されない。
- K：**@import** 構文で外部のファイルを参照し、CLAUDE.md を部品に分ける（例：パッケージごとに関係する規約ファイルだけを取り込む）。
- K：大きな1つの CLAUDE.md の代わりに、話題ごとのルールファイルを置く **.claude/rules/** ディレクトリ。
- S：階層の問題を突き止める（例：指示がプロジェクト単位ではなくユーザー単位に書かれていて、新しいメンバーに届かない）。
- S：各パッケージの CLAUDE.md で @import を使い、担当者の知見に基づいて関係する規約ファイルだけを取り込む。
- S：大きな CLAUDE.md を、.claude/rules/ の話題別のファイル（例：testing.md、api-conventions.md、deployment.md）に分ける。
- S：**/memory** コマンドで、どのメモリファイルが読み込まれているかを確かめ、セッションによって挙動が違う原因を探る。

#### 3.2 Create and configure custom slash commands and skills ［公式］
公式訳：カスタムスラッシュコマンドとスキルを作成し設定する
- K：プロジェクト単位のコマンドは **.claude/commands/**（バージョン管理で共有される）、ユーザー単位のコマンドは **~/.claude/commands/**（個人用）。
- K：**.claude/skills/** の **SKILL.md**。フロントマターで **context: fork**、**allowed-tools**、**argument-hint** を設定できる。
- K：context: fork を付けると、スキルが分離されたサブエージェントの文脈で動き、出力がメインの会話を散らかさない。
- K：個人用に変えたいときは、~/.claude/skills/ に別の名前で作り、チームメイトに影響させない。
- S：チーム全員が使えるように、.claude/commands/ にプロジェクト単位のスラッシュコマンドを作り、バージョン管理で共有する。
- S：出力が長くなるスキル（例：コードベースの分析）や、探索的な文脈を生むスキル（例：別案のブレインストーミング）を、context: fork でメインのセッションから切り離す。
- S：スキルのフロントマターの allowed-tools で、実行中に使えるツールを制限する（例：ファイルの書き込み操作だけに絞って破壊的な操作を防ぐ）。
- S：argument-hint で、引数なしで呼ばれたときに必要なパラメータを入力するよう促す。
- S：スキル（タスクごとのワークフローを必要なときに呼ぶ）と CLAUDE.md（常に読み込まれる共通の標準）を使い分ける。

#### 3.3 Apply path-specific rules for conditional convention loading ［公式］
公式訳：規約を条件付きで読み込むためにパス固有のルールを適用する
- K：.claude/rules/ のファイルに YAML フロントマターの **paths** フィールド（glob パターン）を書き、条件付きでルールを有効にする。
- K：パスを指定したルールは、一致するファイルを編集するときだけ読み込まれ、関係のない文脈とトークンを減らす。
- K：複数のディレクトリにまたがる規約（例：コードベースのあちこちにあるテストファイル）には、ディレクトリ単位の CLAUDE.md より glob パターンのルールが有利。
- S：フロントマターでパスを絞った .claude/rules/ のファイルを作り（例：paths: ["terraform/**/*"]）、一致するファイルの編集時だけ読み込ませる。
- S：パス指定のルールで glob パターンを使い、どのディレクトリにあってもファイルの種類ごとに規約を当てる（例：すべてのテストファイルに **/*.test.tsx）。
- S：コードベースのあちこちにあるファイルに規約を当てるときは、サブディレクトリの CLAUDE.md よりパス指定のルールを選ぶ。

#### 3.4 Determine when to use plan mode vs direct execution ［公式］
公式訳：プランモードと直接実行のどちらを使用するかを判断する
- K：**プランモード**は、大規模な変更、妥当な方法が複数ある、アーキテクチャの判断が要る、複数のファイルにまたがる、といった複雑なタスク向け。
- K：**直接実行**は、単純で範囲がはっきりした変更向け（例：1つの関数に検証のチェックを1つ足す）。
- K：プランモードなら、変更を確定する前に安全にコードベースを調べて設計でき、高くつく手戻りを防げる。
- K：**Explore サブエージェント**で長い調査の出力を切り離し、要約だけを返させてメインの会話の文脈を守る。
- S：アーキテクチャに関わるタスクにはプランモードを選ぶ（例：マイクロサービスへの再構成、45以上のファイルに及ぶライブラリの移行、必要なインフラが違う連携方式の選択）。
- S：内容がよく分かっていて範囲がはっきりした変更には直接実行を選ぶ（例：スタックトレースがはっきりした1ファイルのバグ修正、日付を検証する条件の追加）。
- S：何段階にも分かれるタスクの長い調査フェーズでは Explore サブエージェントを使い、コンテキストウィンドウの使い切りを防ぐ。
- S：調査はプランモード、実装は直接実行と組み合わせる（例：ライブラリの移行を計画し、その計画どおりに実行する）。

#### 3.5 Apply iterative refinement techniques for progressive improvement ［公式］
公式訳：段階的な改善のために反復的な改良手法を適用する
- K：文章の説明が人によって違って受け取られるとき、期待する変換を伝えるには、具体的な入出力の例がいちばん効く。
- K：テスト駆動の反復：先にテストを書き、テストの失敗を共有しながら少しずつ直す。
- K：**インタビューパターン**：実装の前に Claude に質問させ、開発者が見落としていた考慮点を洗い出す。
- K：互いに影響し合う問題は1つのメッセージにまとめて伝え、独立した問題は順番に直す、という使い分け。
- S：自然言語の説明では結果がぶれるとき、2〜3個の具体的な入出力の例で変換の要件をはっきりさせる。
- S：期待する動作、エッジケース、性能の要件を網羅するテストを実装の前に書き、テストの失敗を共有して改善を回す。
- S：不慣れな分野では、インタビューパターンで設計上の考慮点（例：キャッシュの無効化の方針、故障のしかた）を先に洗い出す。
- S：エッジケースの扱いを直すために、入力の例と期待する出力を付けた具体的なテストケースを渡す（例：移行スクリプトでの null 値）。
- S：修正どうしが影響し合うときは複数の問題を1つの詳しいメッセージで伝え、独立した問題は順番に直す。

#### 3.6 Integrate Claude Code into CI/CD pipelines ［公式］
公式訳：Claude CodeをCI/CDパイプラインに統合する
- K：自動のパイプラインで Claude Code を非対話で動かす **-p（--print）フラグ**。
- K：CI で構造化された出力を強制する **--output-format json** と **--json-schema** の CLI フラグ。
- K：CI から呼ばれる Claude Code にプロジェクトの文脈（テストの標準、フィクスチャの慣習、レビューの基準）を渡す手段としての CLAUDE.md。
- K：セッションの文脈の分離：コードを書いたのと同じセッションは、独立したレビュー用のインスタンスに比べて、自分の変更をレビューするのが下手な理由。
- S：CI では -p フラグを付けて動かし、対話の入力待ちで止まるのを防ぐ。
- S：--output-format json と --json-schema で機械が読める形の指摘を出し、PR のインラインコメントとして自動で投稿する。
- S：新しいコミットのあとにレビューし直すときは、前回の指摘を文脈に入れ、新しい問題やまだ直っていない問題だけを報告させて、同じコメントの重複を防ぐ。
- S：既存のテストファイルを文脈に入れ、テスト生成で既にあるシナリオを重ねて提案させない。
- S：テストの標準、価値のあるテストの基準、使えるフィクスチャを CLAUDE.md に書き、テスト生成の質を上げて価値の低い出力を減らす。

### Domain 4: Prompt Engineering & Structured Output（20%）

#### 4.1 Design prompts with explicit criteria to improve precision and reduce false positives ［公式］
公式訳：精度を高め誤検知を減らすために、明示的な基準を備えたプロンプトを設計する
- K：あいまいな指示より明示的な基準（例：「コメントが正しいか確認する」ではなく「コメントが説明する動作が実際のコードの動作と矛盾するときだけ指摘する」）。
- K：「保守的に」「確信度の高いものだけ報告」といった大まかな指示は、具体的なカテゴリの基準ほど精度を上げない。
- K：誤検知が開発者の信頼に与える影響：誤検知の多いカテゴリがあると、正確なカテゴリまで信用されなくなる。
- S：確信度でふるいにかけるのではなく、報告する問題（バグ、セキュリティ）と見送る問題（細かいスタイル、その場所だけのパターン）を定める具体的なレビュー基準を書く。
- S：誤検知の多いカテゴリを一時的に止めて開発者の信頼を取り戻し、その間にそのカテゴリのプロンプトを直す。
- S：重大度ごとに具体的なコード例を付けた明示的な基準を決め、分類をそろえる。

#### 4.2 Apply few-shot prompting to improve output consistency and quality ［公式］
公式訳：出力の一貫性と品質を高めるためにfew-shotプロンプティングを適用する
- K：詳しい指示だけでは出力がそろわないとき、形式がそろって役に立つ出力を得るには few-shot の例がいちばん効く。
- K：few-shot の例で、あいまいなケースの扱いを見せる（例：あいまいな依頼でどのツールを選ぶか、分岐レベルのテストカバレッジの抜け）。
- K：few-shot の例があると、あらかじめ挙げたケースに合わせるだけでなく、新しいパターンにも判断を広げられる。
- K：抽出タスクで、でたらめな値（幻覚）を減らすのにも効く（例：くだけた書き方の寸法、構造がまちまちな文書）。
- S：あいまいな場面に絞った2〜4個の例を作り、もっともらしい別の選択肢ではなくその行動を選んだ理由を見せる。
- S：望む出力の形（場所、問題、重大度、修正案）を示す例を入れて、出力をそろえる。
- S：問題ないコードのパターンと本当の問題を見分ける例を入れ、誤検知を減らしつつ判断を広げさせる。
- S：構造の違う文書（本文中の引用と参考文献の一覧、独立した方法論の節と本文に埋め込まれた詳細）の正しい扱いを例で示す。
- S：形式の違う文書から正しく抽出する例を足し、必須の項目が空や null になる問題を直す。

#### 4.3 Enforce structured output using tool use and JSON schemas ［公式］
公式訳：ツール使用とJSONスキーマを用いて構造化出力を強制する
- K：JSON スキーマ付きの **tool_use** は、スキーマどおりの構造化出力を確実に得るいちばん信頼できる方法で、JSON の構文エラーをなくす。
- K：tool_choice の違い："auto"（ツールを呼ばずにテキストを返すこともある）、"any"（必ずツールを呼ぶが、どれを呼ぶかはモデルが選ぶ）、強制（指名したツールを必ず呼ぶ）。
- K：厳格な JSON スキーマで構文エラーはなくなるが、**意味の誤り**（明細の合計が総額と合わない、値が別の項目に入る）は防げない。
- K：スキーマ設計：必須と任意の項目、拡張できる分類のための enum＋"other"＋詳細の文字列。
- S：JSON スキーマを入力パラメータとする抽出用のツールを定義し、tool_use の応答から構造化データを取り出す。
- S：抽出スキーマが複数あって文書の種類が分からないとき、tool_choice: "any" で構造化出力を保証する。
- S：tool_choice: {"type": "tool", "name": "extract_metadata"} で特定のツールを強制し、情報を付け足す処理より先にその抽出を必ず行わせる。
- S：元の文書にない可能性がある項目は任意（nullable）にして、必須を満たすために値を作り上げるのを防ぐ。
- S：あいまいなケース用の "unclear" や、拡張用の "other"＋詳細の項目を enum に足す。
- S：元データの書式がまちまちなときのために、厳格なスキーマとあわせて、書式をそろえるルールをプロンプトに書く。

#### 4.4 Implement validation, retry, and feedback loops for extraction quality ［公式］
公式訳：抽出品質のための検証、リトライ、フィードバックループを実装する
- K：エラーを伝えるリトライ：リトライのときに具体的な検証エラーをプロンプトに付けて、直す方向を示す。
- K：リトライの限界：必要な情報がそもそも元の文書にない場合は効かない（書式や構造の誤りとは違う）。
- K：フィードバックの仕組み：どのコード構造が指摘を生んだかを記録する **detected_pattern** フィールドで、却下された指摘の傾向を分析できるようにする。
- K：意味の検証エラー（合計が合わない、項目の取り違え）と、スキーマの構文エラー（tool use でなくなる）の違い。
- S：元の文書、失敗した抽出結果、具体的な検証エラーを入れた再リクエストで、モデルに自分で直させる。
- S：リトライが効かない場合（例：必要な情報が、渡していない外部の文書にしかない）と、効く場合（書式の食い違い、出力の構造の誤り）を見分ける。
- S：開発者が指摘を却下したときに誤検知の傾向を分析できるよう、指摘に detected_pattern を持たせる。
- S：自分で直すための検証の流れを設計する：書かれている合計（"stated_total"）と並べて計算した合計（"calculated_total"）を抽出して食い違いを見つける、元データの矛盾には "conflict_detected" の真偽値を付ける。

#### 4.5 Design efficient batch processing strategies ［公式］
公式訳：効率的なバッチ処理戦略を設計する
- K：**Message Batches API**：コストが50%安い、処理に最大24時間かかる、待ち時間の保証（SLA）はない。
- K：バッチは待たなくてよい処理（夜間のレポート、週次の監査、夜間のテスト生成）に向き、待たせる処理（マージ前のチェック）には向かない。
- K：バッチ API は1つのリクエストの中で何往復もツールを呼ぶことができない（途中でツールを実行して結果を返せない）。
- K：リクエストと結果を対応づける **custom_id**。
- S：処理の待ち時間の要件に合わせて API を選ぶ：待たせるマージ前のチェックは同期 API、夜間や週次の分析はバッチ API。
- S：SLA から投入の間隔を計算する（例：処理に最大24時間かかるとき、30時間の SLA を守るには4時間ごとに投入する）。
- S：失敗の処理：custom_id で特定した失敗した文書だけを、必要な手直し（例：コンテキストの上限を超えた文書を分割する）をして出し直す。
- S：大量に流す前にサンプルでプロンプトを磨き、1回目の成功率を上げて、出し直しのコストを減らす。

#### 4.6 Design multi-instance and multi-pass review architectures ［公式］
公式訳：マルチインスタンスおよびマルチパスのレビューアーキテクチャを設計する
- K：セルフレビューの限界：生成したときの推論の文脈を持ったままなので、同じセッションでは自分の判断を疑いにくい。
- K：前の推論の文脈を持たない独立したレビューのインスタンスは、セルフレビューの指示や拡張思考（extended thinking）より、細かい問題を見つけやすい。
- K：マルチパスのレビュー：大きなレビューをファイルごとのローカル分析パスとファイル横断の統合パスに分け、注意の分散や矛盾した指摘を避ける。
- S：生成側の推論の文脈を持たない2つ目の独立した Claude インスタンスで、生成したコードをレビューする。
- S：複数ファイルにまたがる大きなレビューを、局所的な問題を見るファイルごとのパスと、ファイル間のデータの流れを見る統合パスに分ける。
- S：各指摘にモデル自身の確信度を書かせる検証パスを回し、確信度に応じてレビューの振り分けを調整する。

### Domain 5: Context Management & Reliability（15%）

#### 5.1 Manage conversation context to preserve critical information across long interactions ［公式］
公式訳：長いやり取りを通じて重要な情報を保持するために会話コンテキストを管理する
- K：段階的な要約のリスク：数値、割合、日付、顧客が言った期待が、あいまいな要約に縮められてしまう。
- K：「lost in the middle」効果：モデルは長い入力の最初と最後は確実に処理するが、真ん中の発見を落とすことがある。
- K：ツールの結果が文脈にたまり、関係の深さに見合わないほどトークンを使う（例：注文を1回調べると40以上の項目が返るが、要るのは5つ）。
- K：会話の一貫性を保つために、後のリクエストにも会話の履歴をすべて渡す大切さ。
- S：取引の事実（金額、日付、注文番号、ステータス）を、要約した履歴とは別の、ずっと残る「ケースの事実情報（case facts）」ブロックに抜き出し、毎回のプロンプトに入れる。
- S：用件が複数あるセッションでは、構造化した課題のデータ（注文 ID、金額、ステータス）を別の文脈の層に保つ。
- S：長いツールの出力を、たまる前に必要な項目だけに削る（例：注文の検索結果から返品に関係する項目だけを残す）。
- S：まとめた入力の先頭に主な発見の要約を置き、詳しい結果ははっきりした見出しで整理して、位置による取りこぼしを和らげる。
- S：下流の統合を正確にするために、サブエージェントの構造化出力にメタデータ（日付、出典の場所、方法論の文脈）を入れさせる。
- S：下流のエージェントの文脈に余裕がないときは、上流のエージェントが長い本文や推論の過程ではなく、構造化データ（主な事実、引用、関連度のスコア）を返すように変える。

#### 5.2 Design effective escalation and ambiguity resolution patterns ［公式］
公式訳：効果的なエスカレーションと曖昧さの解消のパターンを設計する
- K：エスカレーションすべききっかけ：顧客が人間を求めた、方針の例外や抜け（単に複雑なだけではない）、意味のある前進ができない。
- K：顧客がはっきり求めたらすぐエスカレーションすることと、問題が単純なら自分で解決を申し出ることの違い。
- K：顧客の感情（センチメント）によるエスカレーションや、モデルが自分で申告する確信度が、実際の複雑さを測る目安として当てにならない理由。
- K：顧客の候補が複数見つかったら、推測で選ばずに追加の識別情報を求めて確かめる。
- S：いつエスカレーションし、いつ自分で解決するかを示す明示的な基準と few-shot の例を、システムプロンプトに足す。
- S：顧客が人間の担当者をはっきり求めたら、先に調べようとせずにすぐ応じる。
- S：対応できる範囲の問題なら、不満を受け止めつつ解決を申し出て、顧客が重ねて希望したときだけエスカレーションする。
- S：方針があいまいなときや、顧客の具体的な要望に方針が触れていないときはエスカレーションする（例：方針が自社サイト内の価格調整しか決めていないのに、競合の価格に合わせてほしいと言われた）。
- S：ツールの結果が複数一致したら、手がかりの推測で選ばず、追加の識別情報を尋ねるように指示する。

#### 5.3 Implement error propagation strategies across multi-agent systems ［公式］
公式訳：マルチエージェントシステム全体でのエラー伝播戦略を実装する
- K：構造化したエラーの文脈（失敗の種類、試した問い合わせ、途中までの結果、別のやり方）があれば、コーディネーターが賢く立て直しを判断できる。
- K：アクセスの失敗（リトライするか判断が要るタイムアウト）と、有効な空の結果（正常に検索できたが該当がない）の区別。
- K：汎用のエラー状態（「検索できません」）では、コーディネーターに役立つ文脈が隠れてしまう理由。
- K：エラーを黙って握りつぶす（空の結果を成功として返す）ことも、1つの失敗でワークフロー全体を止めることも、どちらもアンチパターンである理由。
- S：失敗の種類、試したこと、途中までの結果、考えられる別のやり方を含む構造化したエラーの文脈を返し、コーディネーターが立て直せるようにする。
- S：エラーの報告でアクセスの失敗と有効な空の結果を区別し、コーディネーターが適切に判断できるようにする。
- S：サブエージェントが一時的な失敗を自分で立て直し、解決できないエラーだけを、試したことと途中までの結果とあわせて上げる。
- S：統合した出力にカバレッジの注記を付け、よく裏付けられた発見と、情報源が使えずに抜けがある領域を区別する。

#### 5.4 Manage context effectively in large codebase exploration ［公式］
公式訳：大規模なコードベースの探索においてコンテキストを効果的に管理する
- K：長いセッションでの文脈の劣化：答えがぶれ始め、前に見つけた具体的なクラスではなく「よくあるパターン」の話をし始める。
- K：文脈の区切りをまたいで主な発見を残す、**スクラッチパッドファイル**の役割。
- K：長い探索の出力をサブエージェントに任せて切り離し、メインのエージェントは全体の理解をまとめる役に専念する。
- K：クラッシュから立て直すための、構造化した状態の保存：各エージェントが決まった場所に状態を書き出し、再開時にコーディネーターが**マニフェスト**を読み込む。
- S：特定の問い（例：「テストファイルをすべて探す」「返金の処理の依存関係を追う」）をサブエージェントに調べさせ、メインのエージェントは全体の調整を保つ。
- S：主な発見をスクラッチパッドファイルに記録させ、あとの質問で参照させて、文脈の劣化に対抗する。
- S：1つの探索フェーズの主な発見を要約してから次のフェーズのサブエージェントを起動し、その要約を最初の文脈に入れる。
- S：構造化したエージェントの状態の書き出し（マニフェスト）を、再開時にコーディネーターが読み込み、各エージェントのプロンプトに入れる、というクラッシュ復旧を設計する。
- S：長い調査の出力で文脈が埋まってきたら、**/compact** で使用量を減らす。

#### 5.5 Design human review workflows and confidence calibration ［公式］
公式訳：人間によるレビューのワークフローと確信度のキャリブレーションを設計する
- K：全体の精度（例：97%）が、特定の文書の種類や項目での低い性能を隠してしまうリスク。
- K：確信度の高い抽出のエラー率を測り、新しい種類のエラーを見つけるための、層化無作為抽出。
- K：ラベル付きの検証用データで調整した、項目ごとの確信度スコアで、レビューの注意を振り分ける。
- K：確信度の高い抽出を自動化する前に、文書の種類と項目ごとに精度を確かめる大切さ。
- S：確信度の高い抽出に層化無作為抽出をかけ、エラー率を継続して測り、新しいパターンを見つける。
- S：人間のレビューを減らす前に、文書の種類と項目ごとに精度を分析し、どの区分でも安定していることを確かめる。
- S：モデルに項目ごとの確信度を出させ、ラベル付きの検証用データでレビューのしきい値を調整する。
- S：確信度の低い抽出や、元の文書があいまい・矛盾している抽出を人間のレビューに回し、限られたレビューの人手を優先して使う。

#### 5.6 Preserve information provenance and handle uncertainty in multi-source synthesis ［公式］
公式訳：複数の情報源の統合において情報の出所を保持し不確実性に対処する
- K：主張と出典の対応を残さずに発見を縮めると、要約の段階で出典の帰属が失われる。
- K：統合役のエージェントが残してまとめなければならない、構造化した**主張と情報源の対応付け**の大切さ。
- K：信頼できる情報源どうしで統計が食い違うときは、勝手に一方を選ばず、出典を付けて食い違いを書き添える。
- K：時期のあるデータ：構造化出力に公表日や収集日を必須にし、時期の違いが矛盾と誤解されないようにする。
- S：サブエージェントに構造化した主張と出典の対応（出典 URL、文書名、関係する抜粋）を出させ、下流のエージェントが統合を通じてそれを残す。
- S：よく確立した発見と、議論のある発見をはっきりした節で分け、元の情報源の言い方や方法論の文脈を残してレポートを組み立てる。
- S：食い違う値も入れて、それと分かるように注記したまま文書の分析を終え、どう折り合いを付けるかは統合の前にコーディネーターに決めさせる。
- S：サブエージェントの構造化出力に公表日やデータの収集日を入れさせ、時期を正しく読めるようにする。
- S：統合した出力では、内容の種類に合わせて見せ方を変える（財務データは表、ニュースは文章、技術的な発見は構造化したリスト）。すべてを同じ形にしない。

## 6. 範囲内／範囲外

［公式：ガイド v1.0 §17 付録。2026年3月版でも同じ。要約して日本語にした］

### 6-1. 試験に出る可能性のある技術と概念（Technologies and Concepts）

- **Claude Agent SDK**：エージェントの定義、エージェントループ、stop_reason の扱い、フック（PostToolUse、ツール呼び出しの横取り）、Task ツールによるサブエージェントの起動、allowedTools の設定
- **Model Context Protocol（MCP）**：MCP サーバー、MCP ツール、MCP リソース、isError フラグ、ツールの説明、ツールの配り方、.mcp.json の設定、環境変数展開
- **Claude Code**：CLAUDE.md の階層（ユーザー／プロジェクト／ディレクトリ）、YAML フロントマターでパスを指定する .claude/rules/、スラッシュコマンドの .claude/commands/、SKILL.md のフロントマター（context: fork、allowed-tools、argument-hint）を持つ .claude/skills/、プランモード、直接実行、/memory、/compact、--resume、fork_session、Explore サブエージェント
- **Claude Code CLI**：非対話モードの -p／--print、--output-format json、CI で構造化出力を得る --json-schema
- **Claude API**：JSON スキーマ付きの tool_use、tool_choice の選択肢（"auto"、"any"、強制）、stop_reason の値（"tool_use"、"end_turn"）、max_tokens、システムプロンプト
- **Message Batches API**：50%のコスト削減、最大24時間の処理、リクエストと結果を対応づける custom_id、完了を確かめるポーリング、複数ターンのツール呼び出しに非対応
- **JSON Schema**：必須と任意の項目、enum 型、nullable の項目、"other"＋詳細の文字列、構文エラーをなくす strict モード
- **Pydantic**：スキーマの検証、意味の検証エラー、検証してリトライするループ
- **組み込みツール**：Read、Write、Edit、Bash、Grep、Glob の目的と選び方
- **few-shot プロンプティング**：あいまいな場面に絞った例、形式の見本、新しいパターンへの広がり
- **プロンプトチェーン**：焦点を絞ったパスに順番に分ける分解
- **コンテキストウィンドウの管理**：トークンの予算、段階的な要約、lost-in-the-middle、文脈の抜き出し、スクラッチパッドファイル
- **セッション管理**：再開、fork_session、名前付きのセッション、セッションの文脈の分離
- **確信度スコアリング**：項目ごとの確信度、ラベル付きの検証用データによる調整、エラー率を測る層化抽出

### 7-2. 正解の傾向（公式サンプル12問から読み取れること）［筆者の見立て］

1. **根本原因に直接効く、つり合った手当て**が正解。「最初の一手」を問われたら、軽くて効き目の大きい手を選ぶ（Q2、Q3）。
2. 業務上**必ず守らせる必要がある**ルールには、プロンプトではなく**プログラムによる強制（フック、前提条件ゲート）**（Q1）。逆に、判断の線引きがあいまいなだけなら、まず**明示的な基準＋few-shot**（Q3）。この2つの使い分けが繰り返し問われる。
3. **最小の権限・役割の分離**：ツールは役割に必要なものだけ。よく使う用途にだけ範囲を絞ったツールを足す（Q9）。
4. **公式に記載された機能・置き場所**が正解（Q4、Q6、Q10）。もっともらしいが存在しない機能が誤答になる。
5. **情報を落とさない**：エラーの文脈、途中までの結果、出典を構造化して渡す（Q8）。
6. **症状ではなく原因の場所**：複数のエージェントで不具合が出たら、まず上流（コーディネーターの分解）を疑う（Q7）。
7. **処理の性質に合わせる**：待たせる処理と待たせない処理を分ける（Q11）、大きいレビューは分ける（Q12）、複雑な作業は計画から（Q5）。

### 7-3. 「もっともらしいが劣る選択肢」の型 ［筆者の見立て。公式サンプルの誤答から抽出］

| 型 | 中身 | 例 |
|---|---|---|

| B. 作り込みすぎ | 別の分類モデル、キーワードの振り分け層、機械学習の基盤など。効くかもしれないが「最初の一手」には重い | Q2、Q3 |

### 7-4. 問題文の形 ［公式サンプルからの観察］

- 問いの言い方：「最も効果的なのはどれか」「最も効果的な最初の一手はどれか」「最も可能性の高い根本原因はどれか」「最も保守しやすい方法はどれか」「回復を最もよく可能にする方法はどれか」「この提案をどう評価すべきか」。
- 問題文に**本番の数字**が入ることが多い（失敗の割合、解決率と目標、レイテンシの増え方、簡単な確認と難しい確認の比率、ファイル数など）。数字は、どの手当てがつり合っているかを判断する材料になっている。
- 選択肢はどれも「それなりに筋が通る」作り［筆者の見立て］。
- 英語の原文の文字数で数えると、**12問中7問で正解がいちばん長い選択肢**だった（Q1・4・5・6・7・11・12）。ただし、ほとんどの問題で差は数文字〜数十文字と小さい。教材では、正解だけが長く詳しくならないよう選択肢の長さをそろえること［筆者の見立て］。
- **公式サンプル12問のうち10問は正解が A**（Q2 と Q7 だけ B）。教材では正解の位置をばらつかせること［筆者の見立て］。

### 8-2. ガイドの「How to Prepare」（§7）の要旨 ［公式］

1. Agent SDK でエージェントを作る：ツール呼び出し・エラー処理・セッション管理を含む完全なエージェントループ。サブエージェントの起動と文脈の受け渡しも練習する。
2. 実際のプロジェクトで Claude Code を設定する：CLAUDE.md の階層、.claude/rules/ のパス指定ルール、フロントマター（context: fork、allowed-tools）を持つスキル、MCP サーバーを少なくとも1つ。
3. MCP ツールを設計して試す：似たツールを区別できる説明、エラーの種類とリトライ可否を持つ構造化エラー、あいまいな依頼でのツール選択の信頼性のテスト。
4. 構造化データの抽出パイプラインを作る：JSON スキーマ付きの tool_use、検証とリトライのループ、任意（nullable）の項目、Message Batches API でのバッチ処理。
5. プロンプトの技術を練習する：あいまいな場面の few-shot、誤検知を減らす明示的なレビュー基準、大きなコードレビューのマルチパス構成。
6. コンテキスト管理のパターンを学ぶ：長いツール出力からの事実の抜き出し、長いセッションでのスクラッチパッドファイル、文脈の上限に対処するサブエージェントへの委任。
7. エスカレーションと人間が関わるパターンを見直す：エスカレーションするか自分で解決するかの線引き（方針の抜け、顧客の要望、前に進めない）、確信度で振り分ける人間のレビュー。

## 付記：教材を作るうえで気をつけること ［筆者の見立て］

1. **土台は公式ガイド v1.0。** 3月版を写した第三者の教材も、出題範囲としてはそのまま正しい。ただし形式・料金・有効期間の説明は古いことが多い。
2. **用語は公式の日本語訳に合わせる**（3-3、4章の「公式訳」）。日本語で受験する人は、本番でその訳語を見る。英語の原語も並べて書く。
3. **公式サンプル問題の文面を流用しない。** 公開はされているが Anthropic の著作物。同じ論点（7-1 の「正解の考え方」）を、別の状況・別の数字・別のツール名で作り直す。
4. **シナリオの枠組みで出題する。** 本番は6つのシナリオのうち4つが前提になる。練習問題も6つのシナリオに分け、**公式のサンプルがないシナリオ 4（開発者の生産性）と 6（構造化データ抽出）を手厚く**する。
5. **形式は4択・正解1つを中心にし、「2つ選べ」の複数選択式も少し混ぜる。** その場合は選ぶ数を必ず書く。公式に複数選択式の見本はない。
6. **正解の位置をばらつかせ、選択肢の長さもそろえる**（公式サンプルは正解が A に偏り、正解が長めになりがち）。
7. **誤答は 7-3 の型で作る。** でたらめな選択肢ではなく、「効くかもしれないが劣る」「別の問題を解いている」「存在しない機能」を混ぜる。
8. **範囲外を出さない**（6-3）。プロンプトキャッシュの実装、ストリーミング、料金計算、クラウドの設定、ビジョン、コンピュータ使用、ファインチューニング、認証まわり。
9. **製品の仕様の変化に注意。** ガイドは2026年2〜7月時点の書き方（Task ツール、allowedTools、fork_session、.claude/commands/ など）。製品側の名前や仕様がその後変わっている可能性があるが、このメモでは確かめていない。試験はガイドの書き方で出るので、教材はガイドの用語で教え、製品の現状と違う点は注記にとどめるのが安全。
10. **CCDV-F の教材を見直す。** 2026-12-07 に CCDV-F の試験内容が変わり、新しいガイドが 2026-11-17 に出る（O9）。CCAR-F は対象外。
