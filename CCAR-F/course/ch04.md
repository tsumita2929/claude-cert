# 第4章 Claude Code の設定

- 試験: CCAR-F ／ 分野3 Claude Code の設定とワークフロー（20%）／ タスク 3.1、3.2、3.3
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第4章は、分野3の、Claude Code の設定とワークフローです。分野3の配点は20%です。この章では、その前半のタスクステートメント3.1から3.3を扱います。どの指示を、どこに置けば、誰に、いつ届くのか。それを判断できるようになりましょう。

**要点**
- 第4章は分野3の前半、タスク3.1から3.3
- 分野3の配点は20%
- 指示を「どこに置けば、誰に、いつ届くか」を判断する

### チームに届けたい指示は、プロジェクトの CLAUDE.md に書く

CLAUDE.md は、Claude Code が読み込む指示のファイルです。試験ガイドは、3つの階層を挙げています。ユーザーレベルの `~/.claude/CLAUDE.md` は、すべてのプロジェクトで効きますが、効くのは自分だけです。プロジェクトレベルは、リポジトリのルートか、`.claude/CLAUDE.md` に置き、バージョン管理でチームに共有されます。ディレクトリレベルは、サブディレクトリに置いた CLAUDE.md です。

間違えやすいのは、階層の取り違えです。新しいメンバーにだけ規約が届かないなら、規約が誰かのユーザーレベルに書かれていると疑います。直し方は、プロジェクトの CLAUDE.md に移すことです。

セッションごとに挙動が違うときは、`/memory` コマンドで、読み込まれているメモリファイルを確かめます。なお、2026年11月時点では、読み込みの確認に `/context` も案内されています。

**要点**
- ユーザーレベルは自分だけ。チームには共有されない
- プロジェクトレベルはバージョン管理でチームに届く
- 新メンバーに届かないなら、階層の取り違えを疑う
- 読み込まれたメモリファイルは `/memory` で確かめる

### 大きな CLAUDE.md は、@import と .claude/rules/ で分ける

CLAUDE.md が大きくなったら、部品に分けます。1つ目の方法は、`@import` 構文です。アットマークに続けてパスを書くと、そのファイルを取り込めます。各パッケージの CLAUDE.md で、そのパッケージに関係する規約ファイルだけを選んで取り込む、という使い方です。

2つ目は、`.claude/rules/` ディレクトリです。巨大な CLAUDE.md の代わりに、テストの規約は `testing.md`、デプロイの規約は `deployment.md` のように、トピック別のファイルに分けて置きます。

**要点**
- `@import` で外部のファイルを取り込み、部品に分ける
- パッケージごとに、関係する規約ファイルだけを取り込む
- `.claude/rules/` に、トピック別のファイルを置く
- 例は `testing.md` や `deployment.md`

### 散らばったファイルの規約は、paths を付けたルールで当てる

`.claude/rules/` のファイルには、読み込む条件を付けられます。先頭の YAML フロントマターの `paths` に、glob パターンを書きます。glob パターンは、アスタリスクなどでファイル名の形を表す書き方です。こうしたルールは、一致するファイルを扱うときだけ読み込まれるので、関係のない文脈とトークンを減らせます。

たとえば、テストファイルがあちこちのディレクトリに散らばっていても、`**/*.test.tsx` のようなパターンにすれば、場所に関係なく規約が当たります。

もっともらしい誤答は2つです。サブディレクトリごとの CLAUDE.md は、場所に縛られ、同じ内容を何か所にも書くことになります。規約をスキルにすると、呼び出されたときしか読み込まれず、確実に当たりません。なお、試験ガイドは、一致するファイルを編集するときに読み込まれるとしています。2026年11月時点のドキュメントでは、読むときにも読み込まれます。

**要点**
- フロントマターの `paths` に glob パターンを書く
- 一致するファイルを扱うときだけ読み込まれる
- 例は、すべてのテストファイルに当たる `**/*.test.tsx`
- 散らばったファイルには、サブディレクトリの CLAUDE.md より有利

### チームのコマンドは、プロジェクトの .claude/commands/ に置く

カスタムスラッシュコマンドは、スラッシュと名前で呼び出す、決まった手順のプロンプトです。プロジェクトの `.claude/commands/` に置けば、バージョン管理で共有され、クローンした全員が使えます。ホームの `~/.claude/commands/` は、自分だけの個人用です。CLAUDE.md は指示を書く場所で、コマンドを定義する場所ではありません。

スキルは、`.claude/skills/` のフォルダに `SKILL.md` を置きます。チームのスキルを自分好みに変えたいときは、共有のファイルを書き換えず、`~/.claude/skills/` に別の名前で作ります。なお、2026年11月時点では、カスタムコマンドはスキルに統合されていますが、従来のファイルもそのまま動きます。

**要点**
- `.claude/commands/` はバージョン管理でチームに共有
- `~/.claude/commands/` は自分だけの個人用
- スキルは `.claude/skills/` のフォルダに `SKILL.md` を置く
- 個人用の変種は `~/.claude/skills/` に別の名前で作る

### スキルのフロントマターで、実行のしかたを決める

`SKILL.md` のフロントマターで、スキルの動き方を決めます。`context: fork` は、分離されたサブエージェントの文脈で実行します。コードベースの分析のように長い出力や、別案の検討のような探索的な作業を、メインの会話から切り離せます。

`allowed-tools` は、ガイドでは、実行中のツールを絞って破壊的な操作を防ぐ設定です。2026年11月時点のドキュメントでは、確認なしで使えるツールの許可にあたり、取り除くには `disallowed-tools` を使います。`argument-hint` は、必要な引数の入力を促すヒントです。

**要点**
- `context: fork` で、分離したサブエージェントで動かす
- 長い出力や探索的な作業を、メインの会話から切り離す
- `allowed-tools` でスキル実行中のツールを設定する
- `argument-hint` で、必要な引数の入力を促す

### いつも守る標準は CLAUDE.md、必要なときの手順はスキル

使い分けの軸は、その指示が毎回要るかどうかです。全体共通の標準は、常に読み込まれる CLAUDE.md に書きます。特定のファイルだけの規約は、パスを指定したルールです。デプロイのような特定の作業の手順は、必要なときに呼ぶスキルにします。まれにしか使わない長い手順を CLAUDE.md に書くと、毎回の文脈を圧迫します。プランモードなど、進め方の話は第5章で扱います。

**要点**
- CLAUDE.md は常に読み込まれる、全体共通の標準
- スキルは必要なときに呼ぶ、タスク固有のワークフロー
- ファイルの種類で決まる規約は、パスを指定したルール
- まれな長い手順を CLAUDE.md に書かない

### ミニクイズ

それでは、ミニクイズです。

依存関係を洗い出して、長い分析レポートを出すスキルを作りました。ところが実行するたびに、メインの会話が長い出力で埋まってしまいます。最も適切な対応はどれでしょうか。1番、CLAUDE.md に、出力を短くするよう書き足す。2番、スキルのフロントマターに `context: fork` を付ける。3番、スキルを、ホームの `~/.claude/skills/` に移す。

@pause 4

正解は、2番です。スキルが分離されたサブエージェントで動き、メインの会話には結果だけが戻ります。1番は分析そのものを浅くし、3番は置き場所を変えるだけで、問題は解決しません。

### 試験ガイドと現行ドキュメントの食い違い

- `allowed-tools`: ガイドは「スキル実行中のツールアクセスを制限する（例: 破壊的な操作を防ぐ）」と扱う。2026年11月時点の skills ページでは「確認なしで使ってよいツールの事前許可で、使えるツールを制限しない」とされ、取り除くには `disallowed-tools` を使う。本文はガイドの立場を主にし、現行の違いを一言添えた。問題集では、ガイドの立場（制限に使う）で出題し、選択肢に `disallowed-tools` を正解として出さないほうが安全。
- パス指定のルールが読み込まれる時: ガイドは「一致するファイルを編集するときにのみ」。現行の memory ページでは、Read、Write、Edit のどれかで一致するファイルを扱ったとき（読むだけでも）読み込まれる。本文ではガイドの「扱うとき」の言い方を主にし、最後に現行を一言添えた。
- `/memory`: ガイドは「どのメモリファイルが読み込まれているかを確認する」コマンドとして扱う。現行の memory ページでは、ユーザーとプロジェクトのメモリファイルの置き場所を一覧にして開くコマンド（まだないファイルも出る）で、起動時に読み込まれたファイルの確認には `/context all` が案内されている。本文はガイドの立場を主にし、`/context` を一言添えた。
- カスタムコマンド: ガイドは `.claude/commands/` とスキルを別のものとして扱う。現行では「Custom commands have been merged into skills」とされ、`.claude/commands/` のファイルは引き続き動く。本文で一言添えた。
- `argument-hint`: ガイドは「引数なしで呼び出したときに必須パラメータの入力を促す」。現行の skills ページは「入力補完のときに表示される、期待する引数のヒント」とだけ書く。本文は「必要なパラメータを入力するよう促せる」と、両方に合う言い方にした。
- 個人用スキルの名前: ガイドは「別の名前で」作るとする。現行の skills ページでは、同じ名前のスキルが個人用とプロジェクトの両方にあると個人用が優先される（自分の環境でチームのスキルが隠れる）。本文はガイドどおり「別の名前で」とした。
