# 第6章 プロンプト設計とレビュー

- 試験: CCAR-F ／ 分野4 プロンプトエンジニアリングと構造化出力（20%）／ タスク 4.1、4.2、4.6
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第6章は、分野4、プロンプトエンジニアリングと構造化出力の前半です。分野4の配点は20%です。この章では、タスクステートメントの4.1、4.2、4.6を扱います。

テーマは3つです。明示的な基準で、誤検知を減らすこと。few-shot の例で、出力をそろえること。そして、レビューを独立したインスタンスと複数のパスに分けることです。

**要点**
- 分野4（20%）の前半。タスク 4.1、4.2、4.6
- 明示的な基準で誤検知を減らす
- few-shot の例で出力をそろえる
- レビューはインスタンスとパスを分ける

### 「保守的に」ではなく、報告する条件を書く

まず、指示の書き方です。「コメントが正しいか確認して」という指示では、何を問題とするかがあいまいです。試験ガイドは、「コメントが説明する動作が、実際のコードの動作と矛盾するときだけ指摘する」のような、明示的な基準を勧めています。

誤検知を減らしたいとき、「保守的に判断して」や「確信度の高い指摘だけを報告して」と足したくなります。しかし、こうした一般的な指示では、精度は上がりません。何を報告すべきかという基準そのものが、示されていないからです。

代わりに、報告する問題と、見送る問題を、カテゴリで決めます。たとえば、バグとセキュリティの問題は報告する。軽微なスタイルや、その場所だけの書き方の癖は見送る、という具合です。

2026年11月時点の公式ドキュメントも、「重大な問題だけ」のような指示は、見つけたバグの報告漏れにつながるとしています。報告の線を具体的に書くか、すべての指摘を確信度と重大度つきで出させ、別の段階でふるい分ける形を勧めています。

**要点**
- 「正しいか確認」より、指摘する条件を明示する
- 「保守的に」「確信度の高いものだけ」は効かない
- 報告するもの（バグ、セキュリティ）を決める
- 見送るもの（軽微なスタイル）も決める

### 誤検知の多いカテゴリは、いったん止めて直す

誤検知は、件数以上に害があります。あるカテゴリで外れの指摘が続くと、開発者はレビュー全体を信用しなくなります。正確なセキュリティの指摘まで、読み飛ばされるようになります。

そこで、誤検知の多いカテゴリは、一時的に無効にします。ほかのカテゴリへの信頼を取り戻しながら、そのカテゴリのプロンプトを直します。

重大度の分類は、レベルごとに具体的なコード例を付けた基準を書くと、そろいます。

**要点**
- 誤検知の多いカテゴリが、全体の信頼を壊す
- そのカテゴリだけを一時的に止める
- 止めている間に、そのプロンプトを直す
- 重大度はレベルごとにコード例を付けて定義

### 指示でそろわないときは、few-shot の例を見せる

few-shot の例とは、望む入力と出力の見本を、プロンプトの中でいくつか見せる手法です。詳しい指示を書いても出力の形がそろわないとき、試験ガイドは、few-shot の例を最も効果的な手法としています。たとえば、指摘ごとに場所、問題、重大度、修正案を書いた見本を見せれば、形式がそろいます。

例は、判断があいまいな場面に絞ります。ガイドの目安は、2個から4個です。それぞれの例で、もっともらしい別の選択肢ではなく、なぜその対応を選んだのか、という理由まで示します。問題のないコードのパターンと、本当の問題を見分ける例も入れます。理由が分かると、Claude は、例にない新しいパターンにも判断を広げられます。

なお、2026年11月時点の公式ドキュメントは、一般的な目安を3個から5個とし、偏りのない多様な例を勧めています。

**要点**
- 指示でそろわない形式は、few-shot で示す
- 見本の形は、場所、問題、重大度、修正案
- あいまいな場面に絞った例を2〜4個
- 例には、別の選択肢を選ばない理由も書く
- 問題ないパターンと本当の問題を見分ける例

### 抽出でも、例が空欄とでっち上げを減らす

few-shot の例は、文書からの抽出にも効きます。たとえば、引用が本文の中にある論文もあれば、最後に参考文献の一覧を置く論文もあります。方法論が独立した節にある文書もあれば、本文に埋め込まれた文書もあります。

形の違う文書から正しく抜き出す例を見せると、必須の項目が空や null で抽出される問題を減らせます。くだけた書き方の分量を、どう扱うかの例も役立ちます。モデルがもっともらしい値をでっち上げる、ハルシネーションも減ります。抽出のスキーマの設計は、第7章で扱います。

**要点**
- 抽出のハルシネーションも few-shot で減らす
- 構造の違う文書ごとに、正しい抽出例を示す
- 必須の項目が空や null になる問題に効く
- スキーマの設計は第7章

### レビューは、書いた本人ではなく独立したインスタンスにさせる

次は、タスク4.6のレビューの仕組みです。コードを生成したのと同じセッションで、Claude に見直しを頼むとします。これがセルフレビューです。モデルは、生成したときの推論の文脈を持ったままです。そのため、自分の判断を疑いにくくなります。

そこで、生成側の推論の文脈を持たない、独立したレビューインスタンスを使います。試験ガイドは、これが、セルフレビューの指示や拡張思考よりも、微妙な問題を見つけるのに効果的だとしています。考える量を増やしても、生成時の文脈は残ったままだからです。

Claude Code の公式ドキュメントも、会話を見ていない新しいサブエージェントのレビューは、コードを生んだ推論に引きずられない、としています。

**要点**
- セルフレビューは、自分の判断を疑いにくい
- 生成時の文脈を持たない別インスタンスで見る
- セルフレビューの指示や拡張思考より効果的

### 大きなレビューは、ファイル単位のパスと統合パスに分ける

多くのファイルにまたがる変更を、1回でレビューすると、注意の分散が起きます。ファイルによって深さがばらつき、同じコードに矛盾した指摘が出ることもあります。

対策は、マルチパスレビューです。まず、ファイル単位の局所的な分析パスで、1つのファイルの中の問題を見ます。次に、別のファイル横断の統合パスで、ファイルの間のデータの流れを確かめます。

なお、コンテキストウィンドウの大きいモデルに変えても、注意の質の問題は解決しません。同じレビューを何回か回して、一致した指摘だけを残すと、ときどきしか見つからない本物のバグが消えてしまいます。

さらに、各指摘にモデル自身の確信度を添えさせる、検証パスを足す方法もあります。確信度をもとに、どの指摘を人が確かめるかを振り分けます。

**要点**
- 1回の大きなレビューは、注意の分散を招く
- ファイル単位の局所パスで、中の問題を見る
- ファイル横断の統合パスで、データの流れを見る
- 大きなコンテキストや多数決では解決しない
- 検証パスで確信度を添え、振り分けに使う

### ミニクイズ

それでは、ミニクイズです。

CI で動くレビューボットが、命名の規約についての指摘を大量に出しています。その多くが外れで、開発者は、正しいセキュリティの指摘まで無視するようになりました。最も適切な対応はどれでしょうか。1番、プロンプトに「確信度の高い指摘だけを報告して」と書き足す。2番、命名のカテゴリをいったん無効にし、その間に、報告する条件と見送る条件を具体的に書き直す。3番、コンテキストウィンドウの大きいモデルに切り替える。

@pause 4

正解は、2番です。誤検知の多いカテゴリだけを止めれば、ほかの指摘への信頼を取り戻せます。1番のような一般的な指示では、精度は上がりません。

### 試験ガイドと現行ドキュメントの食い違い

- 確信度によるふるい分け: ガイド（タスク 4.1）は「確信度に基づくフィルタリングに頼らず、カテゴリ別の具体的な基準を書く」とする。2026年11月時点のドキュメント（Prompting Claude Opus 4.8 の Code review harnesses）は、新しいモデルでは「重大な問題だけ」「保守的に」が見落としにつながるとして、指摘の段階ではすべてを確信度と重大度つきで出させ、別の検証の段階でふるい分ける構成を勧めている（単一パスなら報告の線を具体的に書く）。曖昧な指示を避け、具体的な線を書く点は両者で一致する。本文はガイドの立場を主にし、現行の助言を一言添えた。ガイドのタスク 4.6 スキル3（確信度を添える検証パス）とも矛盾しない。
- few-shot の例の数: ガイド（タスク 4.2）は「あいまいなシナリオ向けに的を絞った2〜4個」。現行の Prompting best practices は一般的な目安として「3〜5個」。ガイドの数は、あいまいな場面に絞った例についての目安として本文に書き、現行の目安を一言添えた。
- 拡張思考: ガイド（タスク 4.6）は「拡張思考」を比較の対象に挙げる。2026年11月時点のドキュメントでは、`budget_tokens` による従来の extended thinking は legacy の扱いで、新しいモデルは adaptive thinking と `effort` が中心（一部のモデルでは思考が常に有効）。本文はガイドの言い方「拡張思考」のままにし、仕様の細部には触れなかった。
