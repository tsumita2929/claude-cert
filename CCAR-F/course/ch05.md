# 第5章 Claude Code の進め方と CI

- 試験: CCAR-F ／ 分野3 Claude Code の設定とワークフロー（20%）／ タスク 3.4、3.5、3.6

## 本文

### この章で学ぶこと

第5章は、分野3、Claude Code の設定とワークフローの後半です。分野3の配点は20%で、第4章と2回に分けて扱います。この章では、プランモードと直接実行の使い分け、結果を少しずつ良くする伝え方、CI への組み込みを学びます。

**要点**
- 分野3（20%）のタスク 3.4、3.5、3.6
- プランモードと直接実行の使い分け
- 反復的な改良の伝え方
- CI/CD パイプラインへの組み込み

### 複雑さが見えている作業は、プランモードから始める

プランモードは、変更する前に調べて計画を立てるための動き方です。Claude はファイルを読んでコードベースを調べ、計画を書きますが、ソースコードは編集しません。計画を承認してから、編集に移ります。

プランモードが向いているのは、大規模な変更、妥当な方法が複数ある作業、アーキテクチャの判断が要る作業、多くのファイルにまたがる作業です。マイクロサービスへの再構成や、45以上のファイルに及ぶライブラリの移行が、その例です。先に調べて設計すれば、途中で依存関係が見つかってやり直す、という高くつく手戻りを防げます。

一方、直接実行は、範囲がはっきりした単純な変更に向いています。スタックトレースで原因が分かっている1ファイルのバグ修正や、日付を検証する条件を1つ足す作業です。

よくある誤答は、まず直接実行で始めて、難しくなったら切り替える、というものです。複雑さが最初から分かっているなら、最初から計画します。また、2つは組み合わせられます。ライブラリの移行をプランモードで計画し、その計画を直接実行で進めます。

**要点**
- プランモードは調べて計画するだけで、編集しない
- 大規模、複数の方法、設計判断、多数のファイルなら計画から
- 範囲が明確な小さい修正は直接実行
- 複雑さが見えているのに「あとで切り替える」は誤り
- 計画はプランモード、実装は直接実行と組み合わせる

### 長い調査は Explore サブエージェントに任せる

Explore サブエージェントは、コードベースの検索と分析のための、読み取り専用のサブエージェントです。サブエージェントとは、別のコンテキストで作業して、結果だけを返す助手です。

大きなコードベースをメインの会話で調べると、大量の出力がコンテキストに残り続けます。Explore に任せれば、メインには要約だけが戻ります。何段階にも分かれるタスクでは、調査の段階にこれを使い、コンテキストウィンドウを使い切るのを防ぎます。

なお、2026年11月時点のドキュメントは、コンテキストを使い切ることはまれになったとしています。ただ、長い出力を切り離す使い方は、今も勧めています。

**要点**
- Explore は読み取り専用のサブエージェント
- 長い調査の出力を切り離し、要約だけを返す
- 多段階のタスクでコンテキストの枯渇を防ぐ

### 言葉で伝わらないときは、入出力の例とテストで示す

文章で説明しても、受け取り方がぶれ続けることがあります。そのときは、具体的な入力と、期待する出力の例を2つか3つ見せます。期待する変換を伝えるには、これがいちばん効きます。

もう1つは、テスト駆動の反復です。実装の前に、期待する動作、エッジケース、性能の要件を確かめるテストを書きます。そして、失敗したテストの結果を伝えて直させます。移行スクリプトが null 値をうまく扱えないなら、null を含む入力と期待する出力を、テストケースとして渡します。

**要点**
- 説明でぶれるなら、入出力の例を2〜3個示す
- テストを先に書き、失敗を共有して直させる
- エッジケースは入力と期待する出力で伝える

### 不慣れな分野では、実装の前に Claude に質問させる

インタビューパターンとは、実装の前に Claude に質問をさせ、開発者が見落としていた考慮点を洗い出す方法です。なじみのない分野でキャッシュを作るなら、いつ無効にするか、障害のときにどうふるまうか、といった論点を先に確かめられます。

直す問題が複数あるときは、伝え方を選びます。修正どうしが影響し合うなら、1つの詳しいメッセージにまとめて伝えます。別々に直すと、一方の修正がもう一方を壊しかねないからです。独立した問題なら、1つずつ順番に直して確かめます。

**要点**
- インタビューパターンで考慮点を先に洗い出す
- 影響し合う問題は1つのメッセージにまとめる
- 独立した問題は1つずつ順番に直す

### CI では `-p` を付け、構造化された出力を受け取る

CI で Claude Code を動かすときは、`-p` フラグを付けます。長い形の `--print` でも同じです。これで非対話モードになります。付けないと、対話の入力を待ったままジョブが止まります。もっともらしいが存在しない環境変数やフラグは、誤答です。

結果を機械で処理するなら、`--output-format json` を使います。結果が、セッション ID などと一緒に JSON で返ります。さらに `--json-schema` でスキーマを渡すと、それに合った出力が `structured_output` という項目に入ります。指摘ごとにファイル、行、内容を持たせれば、PR のインラインコメントとして自動で投稿できます。

**要点**
- CI では `-p` で非対話にし、入力待ちを防ぐ
- `--output-format json` で機械が読める形にする
- `--json-schema` でスキーマに沿った指摘を出す
- 構造化した指摘を PR のインラインコメントにする

### CI の文脈は CLAUDE.md で渡し、レビューは別のインスタンスに任せる

CI から呼ばれた Claude Code にプロジェクトの決まりを伝える手段が、CLAUDE.md です。テストの標準、価値のあるテストの基準、使えるフィクスチャを書いておくと、テスト生成の質が上がり、価値の低いテストが減ります。フィクスチャとは、テスト用に用意した決まったデータのことです。既存のテストファイルも渡せば、同じシナリオを重ねて提案しなくなります。

なお、2026年11月時点のドキュメントは、CI では `--bare` モードを勧めています。このモードでは CLAUDE.md を自動では読まないので、文脈はフラグで渡します。試験では、ガイドどおり CLAUDE.md を答えにします。

次はレビューです。コードを書いたのと同じセッションは、自分の変更のレビューが苦手です。書いたときの考え方に引きずられるからです。独立したレビューのインスタンスに任せます。新しいコミットのあとにレビューし直すときは、前回の指摘を文脈に入れ、新しい問題とまだ直っていない問題だけを報告させます。これで、コメントの重複を防げます。

**要点**
- テストの標準とフィクスチャは CLAUDE.md に書く
- 既存のテストを渡し、重複したシナリオを防ぐ
- 生成したセッションに自分のレビューをさせない
- 再レビューは前回の指摘を渡し、新規と未対応だけ報告

### ミニクイズ

それでは、ミニクイズです。

CI で、PR に新しいコミットが積まれるたびに、レビューが自動で走ります。すると、前回と同じ指摘が、毎回コメントで付きます。最も適切な対応はどれでしょうか。1番、プロンプトに、重複に注意してと書き足す。2番、前回の指摘を文脈に入れ、新しい問題とまだ直っていない問題だけを報告させる。3番、レビューは PR を開いたときの1回だけにする。

@pause 4

正解は、2番です。1番では、何が前回の指摘なのかを Claude が知りません。3番では、あとから入ったコミットの問題を見逃します。
