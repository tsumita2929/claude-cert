# 第7章 構造化出力とバッチ処理

- 試験: CCAR-F ／ 分野4 プロンプトエンジニアリングと構造化出力（20%）／ タスク 4.3、4.4、4.5
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第7章は、分野4、プロンプトエンジニアリングと構造化出力のうち、タスク4.3から4.5です。分野4の配点は20%です。この章では、Claude の出力を、プログラムで確実に扱う方法を学びます。スキーマで形を強制し、検証とリトライで中身を確かめ、大量の処理はバッチで安く回します。

**要点**
- 分野4（20%）のタスク 4.3、4.4、4.5
- スキーマで出力の形を強制する
- 検証とリトライで中身の質を上げる
- 待てる大量の処理はバッチで安く回す

### 構造化出力は、tool_use と JSON スキーマで強制する

文書から決まった項目を取り出すことを、抽出と言います。試験ガイドが、抽出の結果をスキーマどおりに得る最も信頼できる方法とするのが、ツール使用です。抽出用のツールを定義し、その入力の形を JSON スキーマで書きます。Claude がツールを呼ぶと、`tool_use` ブロックの入力が、そのまま抽出結果になります。JSON の構文の誤りは、これでなくなります。

ツールを確実に呼ばせる設定が、`tool_choice` です。`auto` では、ツールを呼ばずに、テキストで答えることがあります。`any` では、必ずどれかのツールを呼びます。スキーマが複数あり、文書の種類が分からないときに向きます。ツールの名前を指定すると、そのツールを必ず呼びます。ほかの処理の前に、`extract_metadata` での抽出を必ず済ませたいときです。なお、2026年11月時点では、新しいモデルの一部で、この2つの強制が400のエラーになります。その場合は `auto` にして、プロンプトで指示し、ツールに `strict: true` を付けます。

**要点**
- 抽出用ツールの入力を JSON スキーマで定義する
- 結果は `tool_use` ブロックの入力から受け取る
- `auto` はテキストで答えることがある
- 種類が不明で複数スキーマなら `any`
- 特定の抽出を先に必ず行うなら名前を指定

### スキーマは、値をでっち上げさせない形にする

スキーマの設計では、必須と任意の分け方が大事です。文書にないかもしれない項目まで必須にすると、Claude は必須を満たそうとして、値を作り上げることがあります。そうした項目は任意にし、`null` を許します。

分類の項目には、選べる値の一覧である `enum` を使います。一覧にない値に備えて、`other` という値と、詳細を書く文字列を組み合わせます。判断がつかないときのための `unclear` も有効です。また、元の書式がばらばらなら、日付や金額のそろえ方を、正規化のルールとしてプロンプトに書きます。

**要点**
- 文書にないかもしれない項目は任意で `null` 可
- 必須にしすぎると値の捏造を招く
- `enum` に `other` と詳細の文字列を組み合わせる
- 判断できない場合のための `unclear`
- 書式の正規化ルールはプロンプトに書く

### 構文が正しくても、意味の誤りは残る

ただし、スキーマで防げるのは、構文の誤りだけです。明細を足しても、合計と合わない。請求先の住所が、送付先の項目に入っている。こうした意味の誤りも、スキーマの上では正しい JSON です。

そこで、検証の材料を、抽出の段階で出させます。文書に書かれた合計を `stated_total` に、明細から計算した合計を `calculated_total` に、並べて抽出させれば、食い違いをプログラムで見つけられます。元の文書そのものが矛盾しているときのために、`conflict_detected` という真偽値の項目も用意します。

**要点**
- スキーマは構文の誤りをなくすが、意味の誤りは残る
- 合計の不一致や項目の取り違えは別に検証する
- `stated_total` と `calculated_total` を並べて抽出
- 元データの矛盾は `conflict_detected` で示す

### リトライは、直る誤りにだけ効く

検証で誤りが見つかったら、エラーを伝えてリトライします。元の文書、失敗した抽出結果、具体的な検証エラーを、フォローアップのリクエストに入れます。何がどう違うかが分かれば、Claude は自分で直せます。

リトライで直るのは、書式の食い違いや、構造の誤りです。必要な情報が、そもそも文書にない場合は直りません。たとえば、渡していない別紙にしか書かれていない情報です。

指摘を出すタスクでは、各指摘に `detected_pattern` を持たせ、どのコードの構造がきっかけかを記録します。開発者が却下した指摘を、パターンごとに分析できるようになります。

**要点**
- 元の文書、失敗した結果、検証エラーを渡して直させる
- 書式や構造の誤りはリトライで直る
- 文書にない情報はリトライしても出てこない
- `detected_pattern` で却下された指摘の傾向を分析

### バッチは、待てる処理にだけ使う

大量の文書を処理するなら、Message Batches API が候補です。リクエストをまとめて送り、非同期で処理させます。コストは50%安くなりますが、処理には最大24時間かかり、待ち時間の保証、つまり SLA はありません。

使い分けの軸は、誰かが結果を待っているかです。夜間のレポートや週次の監査は、バッチに向きます。プルリクエストのマージ前のチェックは、開発者が待つので、同期の API を使います。また、1つのリクエストの途中で、アプリがツールを実行して結果を返すことはできません。結果は送った順に返るとは限らないので、各リクエストに付けた `custom_id` で対応を取ります。

**要点**
- Message Batches API はコスト50%減、最大24時間
- 待ち時間の保証（SLA）はない
- 夜間・週次の処理はバッチ、マージ前は同期
- 1リクエストの中でツールの往復はできない
- 結果との対応は `custom_id` で取る

### 投入の間隔と出し直しを、先に設計する

バッチの運用では、投入の間隔を SLA から決めます。結果が出るまでの時間は、次の投入までの待ちと、処理の最大24時間の合計です。試験ガイドは、30時間の SLA を守る例として、4時間ごとの投入を挙げています。

失敗したときは、全体ではなく、`custom_id` で特定した失敗分だけを出し直します。コンテキストの上限を超えた文書なら、分割してから送ります。そして、大量に流す前に、サンプルでプロンプトを磨き、1回目の成功率を上げておきます。

**要点**
- 投入までの待ちと処理の24時間の合計で SLA を考える
- 30時間の SLA なら、ガイドの例は4時間ごとの投入
- 失敗分だけを `custom_id` で特定して出し直す
- 上限を超えた文書は分割してから送り直す
- 大量に流す前にサンプルでプロンプトを磨く

### ミニクイズ

それでは、ミニクイズです。

請求書の抽出で、支払い期日の項目が、検証で失敗し続けています。失敗した請求書には「期日は基本契約書による」とだけあり、その契約書は入力にありません。エラーを伝えるリトライを3回しても、直りません。最も適切な対応はどれでしょうか。1番、リトライを5回に増やし、エラーの説明を詳しくする。2番、支払い期日を、`null` を許す任意の項目にする。3番、`tool_choice` で、抽出用のツールを名前で指定する。

@pause 4

正解は、2番です。情報が文書にないので、リトライでは直りません。必須のままでは、値の捏造も招きます。3番は、ツールが呼ばれないという、別の問題への対策です。

### 試験ガイドと現行ドキュメントの食い違い

- **強制のツール選択（`tool_choice` の `any` と名前の指定）。** ガイドは、`any` と `{"type": "tool", "name": …}` を構造化出力を保証する手段として扱う。2026年11月時点の https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools では、Claude Fable 5.2、Mythos 5.2、Opus 5.5、Sonnet 5.5、Fable 5.1、Mythos 5.1 で `any` と `tool` が 400 エラーになり、手動の extended thinking（`thinking: {type: "enabled"}`）でも使えない。代わりに `auto` と strict tool use、または structured outputs を使う。本文はガイドの立場で3つの違いを教え、「新しいモデルの一部で、この2つの強制が400のエラーになる。その場合は `auto` にして、ツールに `strict: true` を付ける」と一言添えた。
- **スキーマへの準拠を何が保証するか。** ガイドは「JSON スキーマを用いたツール使用」を最も信頼できる方法とし、構文エラーがなくなるとする。現行の https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use は「Without strict mode, Claude might return incompatible types (`"2"` instead of `2`) or omit required fields」とし、スキーマへの準拠を保証するのは `strict: true`（制約付きデコード）と、JSON の応答を直接得る structured outputs（`output_config.format`）だとしている。本文はガイドの立場で書き、現行の手段として `strict: true` だけを一言添えた（structured outputs は名前を出していない。スライド・動画で補うなら「2026年11月時点」と添える）。
- **バッチでのツール使用。** ガイドは「単一のリクエスト内でのマルチターンのツール呼び出しをサポートしていない」とする。現行の https://platform.claude.com/docs/en/build-with-claude/batch-processing は、バッチに入れられるものとして「Tool use, including all server tools」と「Multi-turn conversations」を挙げる。これはツールの定義や過去の会話の履歴を入れられるという意味で、アプリ側（クライアント）のツールをリクエストの途中で実行して結果を返すことはできない点は変わらない。サーバーツールは Anthropic 側でリクエストの中で実行される。本文は「アプリがツールを実行して結果を返す往復ができない」と書き、どちらとも矛盾しない形にした。問題集で「バッチではツールを使えない」と言い切らないこと。

### 確認できなかった点

- ガイドの SLA の例（30時間の SLA に対して4時間ごとの投入）で、単純な引き算の上限（30−24＝6時間）ではなく4時間とする理由は、ガイドに説明がない。本文では6時間の計算や理由の推測を書かず、ガイドの例の数字だけを示した。問題集でこの例を使うときは、ガイドの数字（24時間・30時間・4時間）をそのまま使い、別の数字で「正しい間隔」を一意に決める問題にしないほうが安全。
