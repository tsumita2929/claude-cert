# 第3章 ツール設計と MCP 統合

- 試験: CCAR-F ／ 分野2 ツール設計と MCP 統合（18%）／ タスク 2.1〜2.5
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第3章は、分野2、ツール設計と MCP 統合の全体です。配点は18%です。ツールの説明、エラーの返し方、ツールの配り方、MCP サーバーの設定、組み込みツールの選び方の5つを見ます。共通の目的は、モデルが迷わずに正しいツールを選べるようにすることです。

**要点**
- 分野2 ツール設計と MCP 統合、配点は18%
- 説明、エラー、配り方、MCP の設定、組み込みツール
- 目的は、モデルが迷わず正しいツールを選べること

### ツールの説明が、ツール選択の決め手になる

最初は、ツールの説明です。LLM は、ツールの説明を主な手がかりにして、使うツールを選びます。`analyze_content` と `analyze_document` に、ほとんど同じ短い説明しかなければ、呼び先の取り違えが起きます。

直し方は、説明を充実させることです。目的、入力の形式、クエリの例、エッジケース、そして似たツールではなく、これを使うべき場面を書きます。機能が重なるなら、`extract_web_results` のように名前も変えます。汎用のツールは、入出力の決まった目的別のツールに分けます。説明を打ち消す、キーワードに反応する指示がないか、システムプロンプトも見直します。

最初の一手を問われたら、説明の充実を選びます。few-shot の例やキーワードの振り分け層は、重いうえに原因に届きません。

**要点**
- ツールの説明が、ツール選択の主な手がかり
- 目的、入力、例、境界、使い分けを書く
- 重なるツールは、改名と説明の書き直しで分ける
- キーワードに反応する指示がないか、システムプロンプトも見直す

### エラーは、種類とリトライの可否を付けて返す

次は、MCP ツールのエラーです。失敗は、結果に `isError` を付けて伝えます。ただし、どの失敗にも「Operation failed」と返すと、エージェントは次の手を決められません。

そこで、一時的なエラー、検証エラー、ビジネスエラー、権限エラーを区別します。種類を表す `errorCategory`、リトライできるかを表す `isRetryable`、人が読める説明を、構造化して返します。これらは MCP の仕様ではなく、自分で決める項目です。ルール違反には、リトライできないという印と、顧客向けの説明を付けます。

一時的な失敗は、サブエージェントの中で立て直します。解決できないものだけを、途中の結果と試したことと一緒に、コーディネーターへ伝えます。また、該当なしという正常な空の結果は、アクセスの失敗と区別して返します。

**要点**
- 失敗は `isError` で伝え、中身を構造化する
- 一時的、検証、ビジネス、権限のエラーを区別する
- リトライできるかを、構造化して返す
- 該当なしの成功と、アクセスの失敗を分ける

### ツールは、役割に必要なものだけを渡す

3つ目は、ツールの配り方です。4から5個ではなく18個ものツールを渡すと、選択の信頼性が下がります。専門外のツールは誤用されがちで、たとえば統合エージェントがウェブ検索を始めてしまいます。

そこで、各サブエージェントには、役割に必要なツールだけを渡します。汎用の `fetch_url` は、文書の URL かを検証する `load_document` のような、制約付きのツールに置き換えます。頻度の高い用途だけは、統合エージェントへの `verify_fact` のように、範囲を絞った横断のツールを渡し、複雑な確認はコーディネーター経由のままにします。

`tool_choice` は3種類です。`auto` は、使うかどうかをモデルに任せます。`any` は、必ずどれかのツールを呼ばせます。名前を指定する強制は、たとえば `extract_metadata` を最初に呼ばせ、続きは次のターンで処理します。なお、2026年11月時点では、新しいモデルの一部で、`any` と名前の指定がどちらもエラーになります。その場合は、`auto` とプロンプトでの指示や、`strict: true` で代えます。

**要点**
- ツールが多すぎると、選択の信頼性が下がる
- 各サブエージェントには、役割に必要なツールだけ
- 頻度の高い用途だけ、範囲を絞った横断ツールを足す
- `tool_choice` は `auto`、`any`、特定ツールの強制

### MCP サーバーは、共有はプロジェクトに、個人用はユーザーに置く

4つ目は、MCP サーバーの設定です。チームで共有するサーバーは、プロジェクトの `.mcp.json` に書いてコミットします。個人用や試験的なものは、ユーザーの `~/.claude.json` に置きます。トークンは直接書かず、`${GITHUB_TOKEN}` のような環境変数の展開で渡します。

設定したすべてのサーバーのツールは、接続時に検出され、同時に使えます。2026年11月時点の Claude Code では、定義を必要なときに読み込むツール検索が既定です。

組み込みの Grep ばかり選ばれるなら、MCP ツールの説明に、機能と出力を詳しく書きます。Jira のような標準の連携には、既存のコミュニティ製サーバーを選び、自作はチーム固有の作業に取っておきます。課題の要約やデータベースのスキーマのような目録は、MCP リソースとして公開し、手探りの呼び出しを減らします。

**要点**
- 共有は `.mcp.json`、個人用は `~/.claude.json`
- トークンは環境変数の展開で渡し、コミットしない
- MCP ツールの説明を詳しくし、組み込みツールに負けないようにする
- 標準の連携はコミュニティ製、自作はチーム固有に
- コンテンツの目録は、MCP リソースで見せる

### 中身は Grep、名前は Glob、部分の修正は Edit

最後は、Claude Code の組み込みツールです。ファイルの中身、たとえば関数の呼び出し元を探すなら Grep。名前や拡張子のパターンでファイルを探すなら Glob。コマンドの実行は Bash です。全体の読み書きは Read と Write、部分の修正は Edit です。Edit は、一意に一致するテキストを目印に置き換えるので、同じテキストが何か所もあると失敗します。そのときは、Read で全体を読んでから、Write で書きます。

コードベースは、最初に全部を読みません。Grep で入口を見つけ、Read で import をたどります。ラッパーを経由する関数は、エクスポートされた名前を洗い出してから、それぞれを検索します。なお、2026年11月時点の Claude Code では、macOS などで Grep と Glob が既定から外れ、Bash で検索します。

**要点**
- 中身の検索は Grep、ファイル名のパターンは Glob
- 全体の読み書きは Read と Write、部分の修正は Edit
- Edit の目印が一意でなければ、Read してから Write
- Grep で入口を見つけ、Read で import をたどる

### ミニクイズ

それでは、ミニクイズです。

社内文書を検索する MCP ツールが、該当なしのときも、接続に失敗したときも、同じ空の結果を返すため、エージェントが接続の失敗に気づかず、該当なしと答えてしまいます。最も適切な直し方はどれでしょうか。1番、結果が空なら3回までやり直すよう、システムプロンプトに書く。2番、接続の失敗は `isError` とリトライの可否を付けて返し、該当なしは成功として返す。3番、どんなエラーでも例外を投げ、処理全体を止める。

@pause 4

正解は、2番です。区別すれば、エージェントは、やり直すか、そのまま答えるかを選べます。1番は無駄なリトライを生み、3番は立て直しの機会を奪います。

### 試験ガイドと現行ドキュメントの食い違い

- **`tool_choice` の強制。** ガイドは `any` と `{"type": "tool", "name": …}` を、ツールを確実に呼ばせる手段として扱う。2026年11月時点の define-tools のページでは、Claude Fable 5.2、Mythos 5.2、Opus 5.5、Sonnet 5.5、Fable 5.1、Mythos 5.1 で `any` と `tool` が 400 エラーになり、手動の extended thinking でも使えない。代わりは `auto`（strict tool use と組み合わせる、プロンプトで誘導する）か structured outputs。本文はガイドの3つの選択肢を主に教え、「新しいモデルの一部で、`any` と名前の指定がどちらもエラーになり、`auto` とプロンプトでの指示や `strict: true` で代える」と一言添えた。
- **MCP ツールの読み込み。** ガイドは「設定したすべての MCP サーバーのツールが接続時に検出され、同時に利用可能になる」とする。2026年11月時点の Claude Code では tool search が既定で、セッションの開始時にはツールの名前とサーバーの説明だけが読み込まれ、定義は必要なときに読み込まれる（`ENABLE_TOOL_SEARCH=false` で全部を最初に読み込む）。本文はガイドの記述を主にし、「定義を必要なときに読み込むツール検索が既定」と一言添えた。
- **MCP サーバーのスコープ。** ガイドはプロジェクト（`.mcp.json`）とユーザー（`~/.claude.json`）の2つで説明する。現行の Claude Code には local（既定。そのプロジェクトだけで自分だけが使う。これも `~/.claude.json` に保存）、project、user の3つがあり、ドキュメントは試験的な設定や秘密情報を含むサーバーには local を勧めている。本文はガイドの2分類のみを書いた（字数の都合）。問題集では「個人用・試験的なら `~/.claude.json`」というガイドの立場で正解を作り、local スコープを誤答の根拠にしないこと。
- **組み込みツールの Grep と Glob。** ガイドは Read、Write、Edit、Bash、Grep、Glob の6つを前提にする。2026年11月時点の Claude Code では、macOS、Linux、WSL で Grep と Glob が既定のツールから外れ、Bash の `find` と `grep`（組み込み版の bfs と ugrep）で検索する。`--tools` や `--allowedTools` で名前を挙げる、サブエージェントの `tools` に挙げて Bash を外す、などで戻る。本文は「macOS などで既定から外れ、Bash で検索する」と一言添えた。試験ではガイドの6つのツールで考える。
- **Edit の一意性。** ガイドは、一意に一致しないときの代わりの手段を Read と Write とする。現行の Edit には、すべての一致を置き換える `replace_all: true` と、前後の文脈を足して一意にするやり方もある。本文はガイドの立場だけを書いた。
- **（食い違いではないが注意）ツールの統合と分割。** ガイドは、あいまいな汎用ツールを入出力の約束が決まった目的別ツールに分ける（2.1）。define-tools のページは、関連する操作を `action` パラメータで1つのツールにまとめ、ツールの数を減らすことも勧めている。どちらも「選択のあいまいさを減らす」という同じ目的。問題集でこの2つを対立させる問題は作らないほうが安全。
- **MCP のエラーの分類（仕様の版の違い）。** 2025-06-18 版の仕様は「Invalid arguments」をプロトコルエラーの例に挙げていたが、現行（2026-07-28 版）は入力の検証エラーを、`isError: true` のツール実行エラーに含める。ガイドの「検証エラー」をツールの結果で返す扱いと合うのは現行版。本文では版に触れていない。
