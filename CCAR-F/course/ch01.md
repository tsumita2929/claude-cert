# 第1章 エージェントループと制御

- 試験: CCAR-F ／ 分野1 エージェントアーキテクチャとオーケストレーション（27%）／ タスク 1.1、1.4、1.5
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第1章は、分野1、エージェントアーキテクチャとオーケストレーションのうち、タスクステートメント1.1、1.4、1.5を扱います。分野1の配点は27%で、5つの分野の中で最大です。

ループの回し方と止め方、ワークフローの順序の守らせ方、そして Agent SDK のフックを学びます。芯になる考え方は1つです。必ず守らせたいことは、プロンプトではなく、仕組みで強制します。

**要点**
- 分野1は配点27%で、5分野の中で最大
- この章はタスク1.1、1.4、1.5を扱う
- 芯は「必ず守らせたいことは仕組みで強制する」

### エージェントループは stop_reason を見て回す

エージェントループとは、Claude にリクエストを送り、求められたツールを実行し、結果を返して、また判断させる繰り返しです。1周ごとに、応答の `stop_reason` を確かめます。`tool_use` なら、ツールを実行してループを続けます。`end_turn` なら、Claude が応答を終えたので、ループを終えます。

ツールの結果は、会話履歴に追加します。Claude の応答を、ツールの呼び出しごと履歴に戻し、続くユーザーのメッセージで `tool_result` を返します。どの呼び出しへの結果かは、`tool_use_id` で対応づけます。こうして Claude は、新しい情報をもとに次の一手を考えます。

これを、モデル主導の意思決定と呼びます。次に呼ぶツールを、Claude が文脈から推論します。あらかじめ決めた決定木や、固定のツールの順番とは違います。

**要点**
- `tool_use` なら続け、`end_turn` なら終える
- 応答と結果を会話履歴に足し、次の周に渡す
- 結果は `tool_use_id` で呼び出しと対応づける
- 次のツールは Claude が文脈から選ぶ

### 終了を、文章の中身や回数の上限で決めない

試験ガイドは、ループの止め方について、3つのアンチパターン、つまり典型的な失敗の型を挙げています。

1つ目は、「完了しました」のような言葉を解析して止めることです。言い回しは毎回変わるので、確実ではありません。2つ目は、テキストがあるかどうかで完了と見なすことです。Claude は、前置きの文章とツールの呼び出しを、同じ応答で返すことがあります。3つ目は、根拠のない反復回数の上限を、主な停止手段にすることです。作業の途中でも切れてしまいます。

判断の軸は、いつも `stop_reason` です。回数の上限は、暴走を防ぐ安全網として置きます。Agent SDK の `max_turns` も、その用途の上限です。なお、2026年11月時点のドキュメントでは、`tool_use` 以外の理由で止まればループを抜け、`max_tokens` による打ち切りなどは、完了と区別して扱うと説明しています。

**要点**
- 「完了」などの言葉を解析して止めない
- テキストの有無を完了の目印にしない
- 回数の上限は安全網で、主な停止手段ではない
- 判断の軸は、いつも `stop_reason`

### 必ず守らせる順序は、前提条件ゲートで強制する

次は、タスクステートメント1.4、複数ステップのワークフローです。サポートのエージェントで、返金の前に必ず本人確認をしたいとします。システムプロンプトに書けば、Claude はたいてい従います。しかし、プロンプトの指示だけでは、失敗率はゼロになりません。お金の操作でまれにでも順番が飛ぶと、別人の口座への返金のような事故になります。

そこで、プログラムによる強制を使います。代表が前提条件ゲートで、前のステップが終わるまで、後ろのツールをコードで止めます。ガイドの例では、`get_customer` が確認済みの顧客IDを返すまで、`process_refund` を実行させません。

判断の軸は、決定論的な遵守、つまり毎回必ず守らせることが要るかどうかです。外せない規則はプログラムで強制し、多少ぶれてよいことはプロンプトで誘導します。プロンプトを強める、例を足す、という選択肢は、確率的な手当てなので、必ず守らせる場面では劣ります。

**要点**
- プロンプトの指示だけでは、失敗率はゼロにならない
- 前提条件ゲートで、後ろのツールをコードで止める
- 例: 本人確認が済むまで返金のツールを止める
- 外せない規則は強制、ぶれてよいことは誘導

### 人へ引き継ぐときは、構造化したサマリーを渡す

途中で人間の担当者に回す、エスカレーションの場面もあります。前提は、担当者が会話の記録を見られないことです。そこで、構造化されたハンドオフサマリー、つまり引き継ぎの要約を渡します。ガイドが挙げる項目は、顧客ID、根本原因、返金額、推奨する対応です。

1つの問い合わせに、複数の用件が含まれることもあります。その場合は、用件を個別の項目に分け、共有の文脈を使って並行して調べ、ひとつの解決策にまとめます。

**要点**
- 引き継ぐ相手は、会話の記録を見られない前提
- 顧客ID、根本原因、返金額、推奨する対応を渡す
- 複数の用件は分けて並行に調べ、1つにまとめる

### フックで、ツールの呼び出しと結果に割り込む

最後は、タスクステートメント1.5、Agent SDK のフックです。フックとは、エージェントの動きの決まった時点で、自分のコードを実行する仕組みです。アプリの側で動くコードなので、モデルの判断に左右されず、決定論的に効きます。

1つ目は、出ていくツールの呼び出しを、インターセプト、つまり横取りする使い方です。ツールの実行前に呼ばれる `PreToolUse` フックで、たとえば500ドルを超える返金を止め、人へのエスカレーションに回します。止めた理由は Claude に伝えられるので、Claude は別のやり方に切り替えられます。

2つ目は、ツールの結果を、モデルが処理する前に変換する使い方です。結果が返ったあとに呼ばれる `PostToolUse` フックで、たとえば MCP ツールごとにばらばらな日時の形式を、1つにそろえます。Unix タイムスタンプと ISO 8601 が混ざっている、といった場面です。これを正規化と呼びます。

業務ルールで確実な遵守が要るなら、プロンプトではなくフックを選びます。

**要点**
- フックはアプリ側のコードで、決定論的に効く
- `PreToolUse` で方針違反の呼び出しを止め、人に回す
- `PostToolUse` でばらばらな結果の形式をそろえる
- 確実な遵守が要るなら、プロンプトよりフック

### ミニクイズ

それでは、ミニクイズです。

あるエージェントが、ときどき作業の途中で止まります。止まったときの応答には、在庫を調べます、という文章と、在庫を調べるツールの呼び出しが入っていました。最も可能性の高い原因はどれでしょうか。1番、反復回数の上限が小さすぎる。2番、文章があるかどうかで完了を判定している。3番、ツールの結果を会話履歴に追加していない。

@pause 4

正解は、2番です。文章とツールの呼び出しは、同じ応答に入ることがあります。`stop_reason` が `tool_use` なら、ループを続けます。

### 試験ガイドと現行ドキュメントの食い違い

- `stop_reason` の扱い。ガイドは `tool_use` と `end_turn` の2つだけを扱う。2026年11月時点のドキュメントは7つの値（`end_turn`、`max_tokens`、`stop_sequence`、`tool_use`、`pause_turn`、`refusal`、`model_context_window_exceeded`）を挙げ、`tool_use` 以外ならループを抜けて、理由ごとに扱うよう説明している（`pause_turn` はサーバーツールのループの中断で、続けて送り直す）。本文はガイドどおり「`tool_use` なら続け、`end_turn` なら終える」を主にし、「`tool_use` 以外で止まったら抜ける。`max_tokens` のような打ち切りは完了と別に扱う」と一言添えた。矛盾ではなく、現行の説明のほうが細かい。
- `PostToolUse` で結果を差し替える方法。ガイドは仕組みだけを述べる。現行のドキュメントでは、`hookSpecificOutput` の `updatedToolOutput`（組み込みツールと MCP ツールの両方）で差し替え、`additionalContext` で情報を足す。古い `updatedMCPToolOutput` は MCP ツールだけ。本文ではフィールド名を出していない（試験ガイドにないため）。
- 参考（この章の範囲外）。現行の Agent SDK のドキュメントでは、サブエージェントを起動する組み込みツールは `Agent` と書かれている（agent-loop の組み込みツールの表「Orchestration: Agent … Spawn subagents」）。ガイドのタスク 1.3 は `Task` ツールと書く。第2章の担当は確認のこと。
