# 第8章 コンテキスト管理と信頼性

- 試験: CCAR-F ／ 分野5 コンテキスト管理と信頼性（15%）／ タスク 5.1〜5.6
- 確認日: 2026-11-16

## 本文

### この章で学ぶこと

第8章は、分野5の、コンテキスト管理と信頼性です。配点は15%です。タスクステートメント5.1から5.6までの6つを、1つずつ見ていきます。共通する軸は、情報を落とさずに、判断できる相手へ渡すことです。

**要点**
- 分野5 コンテキスト管理と信頼性は配点15%
- タスクは5.1〜5.6の6つ
- 共通の軸は「情報を落とさず、判断できる相手へ渡す」

### 取引の事実は、要約の外に置く

長い対話では、古いやり取りを要約して、コンテキストを節約します。ただ、要約を重ねると、金額や日付、顧客が言った期待が、あいまいな言葉に縮んでしまいます。そこで、取引の事実は、要約とは別の「ケースの事実情報」ブロックに抜き出し、毎回のプロンプトに入れます。用件が複数あれば、用件ごとに構造化して保ちます。

ツールの結果もたまります。注文を1回調べると40以上の項目が返るのに、返品に要るのは5つだけ、ということがあります。たまる前に、必要な項目だけに削ります。

モデルは、長い入力の最初と最後はよく読みますが、真ん中を落とすことがあります。これを lost in the middle と呼びます。主な発見の要約を先頭に置き、詳細は見出しで整理します。なお、Messages API は状態を持たないので、会話を続けるときは、履歴をすべて毎回送ります。

**要点**
- 要約を重ねると、数値・日付・期待があいまいになる
- 取引の事実は「ケースの事実情報」ブロックで毎回渡す
- ツール出力は、たまる前に必要な項目だけに削る
- 長い入力は、要約を先頭に置き見出しで整理する

### 人を求められたら、すぐに引き継ぐ

次は、エスカレーション、つまり人の担当者への引き継ぎです。きっかけは、顧客が人を求めたとき、方針に例外や抜けがあるとき、前進できないときです。単に複雑なだけでは、きっかけになりません。

顧客がはっきり人を求めたら、調べる前にすぐ応じます。不満を述べているだけで、対応できる問題なら、気持ちを受け止めて解決を申し出て、重ねて求められたら引き継ぎます。方針が触れていない要望も引き継ぎます。たとえば、方針が自社サイトの価格調整しか決めていないのに、競合の価格に合わせてほしい、と言われた場合です。

劣るのは、顧客の感情や、モデルが自己申告する確信度で決めるやり方です。どちらも、複雑さの目安になりません。基本は、明示的な基準と few-shot の例を、システムプロンプトに書くことです。候補の顧客が複数見つかったら、推測で選ばず、追加の識別情報を尋ねます。

**要点**
- きっかけは、人の要求、方針の例外や抜け、前進できない
- 人を求められたら、調べる前にすぐ引き継ぐ
- 感情や自己申告の確信度は、複雑さの目安にならない
- 候補が複数なら、推測せず追加の識別情報を尋ねる

### エラーは、文脈ごとコーディネーターに返す

マルチエージェントでは、サブエージェントの失敗の伝え方が問われます。失敗の種類、試した問い合わせ、途中までの結果、別のやり方を、構造化して返します。そうすれば、コーディネーターが立て直し方を判断できます。このとき、タイムアウトのようなアクセスの失敗と、検索は成功したが該当がない、有効な空の結果を区別します。

誤答の型は、両極端です。空の結果を成功として返して、エラーを握りつぶす。1つの失敗で、全体を止める。「検索を利用できません」とだけ返す。どれも劣ります。一時的な障害はサブエージェントの中で立て直し、直らないものだけを上げます。最後のレポートには、情報源が足りなかった領域を注記します。

**要点**
- エラーは種類・試行・途中の結果・代替案を付けて返す
- アクセスの失敗と、有効な空の結果を区別する
- 握りつぶしも、全体の停止も、アンチパターン
- 一時的な障害は手元で直し、直らないものだけ上げる

### 長い探索は、ファイルとサブエージェントで支える

大きなコードベースを長く調べると、コンテキストが劣化します。前に見つけた具体的なクラスではなく、「よくあるパターン」の話をし始めたら、そのサインです。

対策の1つは、スクラッチパッドファイルです。主な発見をファイルに書き留めさせ、あとの質問で参照させます。ファイルは文脈の外にあるので、区切りをまたいで残ります。もう1つは、サブエージェントへの委任です。「テストファイルをすべて探す」のような問いを任せれば、長い出力はサブエージェントの側にとどまり、メインは全体の調整に専念できます。

クラッシュに備えて、各エージェントは決まった場所に状態を書き出し、再開時にコーディネーターが、その目録であるマニフェストを読み込みます。Claude Code で文脈が埋まってきたら、`/compact` で会話を要約して減らします。

**要点**
- 劣化のサインは「よくあるパターン」の話をし始めること
- 主な発見はスクラッチパッドファイルに残す
- 特定の問いはサブエージェントに任せ、出力を切り離す
- 再開はマニフェストから。埋まってきたら `/compact`

### 全体の精度ではなく、区分ごとの精度を見る

抽出の自動化では、人のレビューをどこまで減らせるかが問われます。全体の精度が97%でも、特定の文書の種類や項目で、低い精度が隠れていることがあります。レビューを減らす前に、区分ごとに精度を確かめます。

確信度は、モデルに項目ごとに出させ、正解付きの検証用データで、レビューに回すしきい値を調整します。これが、確信度のキャリブレーションです。確信度が低い抽出や、元の文書があいまいな抽出を、限られた人手に優先して回します。確信度の高い抽出も、層化無作為抽出、つまり区分ごとに偏りなくサンプルを取って調べ、エラー率を測り続けます。

**要点**
- 全体97%でも、特定の区分の低さが隠れることがある
- レビューを減らす前に、文書の種類と項目ごとに確かめる
- 確信度のしきい値は、ラベル付きの検証用データで調整
- 確信度の高い抽出も、層化無作為抽出で測り続ける

### 主張と出典を、最後まで対応させる

複数の情報源をまとめるとき、主張と出典の対応を残さずに要約すると、出典が分からなくなります。そこで、サブエージェントに、主張ごとに出典の URL、文書名、抜粋を構造化して出させ、統合役はその対応を残してマージします。公表日も出させ、時期の違いを矛盾と取り違えないようにします。

信頼できる情報源どうしで数値が食い違ったら、一方を選ばず、両方を出典付きで残して注記します。折り合いの付け方は、コーディネーターが決めます。レポートでは、確立した発見と議論のある発見を分けて書きます。財務データは表、ニュースは文章のように、見せ方も内容に合わせます。

**要点**
- 主張ごとに、出典の URL・文書名・抜粋を構造化して渡す
- 公表日で、時期の違いを矛盾と取り違えない
- 食い違う値は、出典付きで両方残して注記する
- 確立した発見と、議論のある発見を分けて書く

### ミニクイズ

それでは、ミニクイズです。

文書分析のサブエージェントが、ある市場の規模について、信頼できる2つの報告書から違う数値を見つけました。2年前の報告書と、今年の報告書です。最も適切な対応はどれでしょうか。1番、新しいほうの数値だけを返す。2番、2つの平均を返す。3番、両方の数値を、出典と公表日を付けて返し、食い違いを注記する。

@pause 4

正解は、3番です。公表日があれば、時期による差か本当の食い違いかを、コーディネーターが判断できます。一方を選んだり平均したりすると、その判断の材料が消えます。

### 試験ガイドと現行ドキュメントの食い違い

- 会話履歴の渡し方：試験ガイド（タスク 5.1）は「後続の API リクエストで完全な会話履歴を渡すことの重要性」を挙げる。2026年11月時点の Messages API のドキュメントも「stateless で、毎回すべての履歴を送る」と書くが、同じページに、ベータの message threads を使うと API 側で会話を保ち、新しいメッセージだけを送ればよいとある。本文はガイドの立場（履歴をすべて送る）だけを書き、ベータの機能には触れていない。問題集では「履歴を送らなくてよい」を正解にしないこと。
- サブエージェントを起動するツールの名前：試験ガイド（タスク 1.3 と付録）は `Task` ツールと書くが、Claude Code のドキュメントでは v2.1.63 で `Agent` ツールに名前が変わった（`Task` は別名として残る）。本章の本文ではツール名に触れていない。第2章と問題集の担当向けの記録。

### 確認できなかった点

- 「lost in the middle」という名前と、長い入力の真ん中を落としやすいという性質は、試験ガイドの記載に拠った。Anthropic の現行ドキュメントでこの名前を使う箇所は見つけられなかった（ドキュメントは「長い文書を先頭に、質問を後ろに置く」と助言する）。本文はガイドどおりに書いた。
- タスク 5.2、5.5 の具体的な手当て（エスカレーションの基準、層化無作為抽出、確信度のキャリブレーション）は、試験ガイド以外の Anthropic の一次情報で同じ書き方の箇所を見つけていない。ガイドの記載だけを根拠にした。
