# 声（音声エンジン）

ナレーションは、ローカルで動く音声合成エンジンで作る。原稿を外部に送らず、費用もかからない。

| 名前 | エンジン | 特徴 | ポート |
|---|---|---|---|
| `voicevox` | VOICEVOX | 声の種類が多い（約45キャラクター）。読みが安定している | 50021 |
| `aivis` | AivisSpeech | 人の話し方に近い。声の種類は少なめ（追加できる） | 10101 |
| `say` | macOS 標準の読み上げ | 仮の音声用。品質は低い | なし |

## 起動と停止

`voice`・`audition`・`speakers` は、必要なエンジンを自動で起動する。手で操作するときは次のとおり。

```bash
cv engine status            # 起動しているか
cv engine start voicevox    # 起動（初回は Docker のイメージ取得で数分〜十数分）
cv engine stop              # 全部止める（メモリを空ける）
```

- Docker Desktop が起動している必要がある。イメージは VOICEVOX が約2.4GB、AivisSpeech が約3.7GB。
- VOICEVOX や AivisSpeech の**デスクトップアプリを開いていれば、それを使う**（同じポートで待ち受けるため）。Docker は不要になる。
- 使い終わったら `engine stop` で止めてよい。次に必要になれば自動で起動する。

## 声を選ぶ（聴き比べ）

声は文字では選べない。**必ずユーザーに聴いて選んでもらう。**

```bash
cv speakers voicevox               # 声の一覧（名前とスタイルの番号）
cv speakers voicevox --policy 500  # 利用規約の冒頭も表示
cv audition video \
  --text 'リクエストの必須パラメータは、3つです。使うモデルを表す、model。' \
  --voices voicevox:13:speed=1.1 voicevox:11:speed=1.1 aivis:888753760
```

- `--text` には、**実際の台本から用語を含む2〜3文**を使う。用語の読み方で声の印象が変わるため。
- `--voices` は `エンジン:番号[:speed=1.1]` の形。6〜10個が聴き比べやすい。
- できた `video/out/_audition/index.html` を `open` で開き、番号で答えてもらう。音量はそろえてある。
- 講義には、落ち着いた声が向く。キャラクター色の強い声は、内容より声が印象に残りやすい。ただし決めるのはユーザー。

決まったら `video/project.json` に書く。

```json
"voice": {"engine": "voicevox", "speaker": 13, "speed": 1.08},
"credit": "VOICEVOX:青山龍星"
```

`credit` には、概要欄の「音声:」の後ろに入れる文言だけを書く（「音声:」は含めない）。
AivisSpeech の声なら `"AivisSpeech（コハク）"` のように書く。

## 利用規約を確かめる

声ごとに条件が違う。**YouTube で収益化する動画は商用利用にあたる**ので、候補に入れる前に確かめる。

- `cv speakers <エンジン> --policy 4000` で、各声の規約がほぼ全文読める。前文が長い規約（ACML など）は、
  営利利用やクレジットの条項が後ろのほうにあるので、冒頭だけで判断しない。
- VOICEVOX の声の多くは「`VOICEVOX:キャラクター名` とクレジットを書けば、商用・非商用で利用可」。
  ただし声によって「商用は事前確認が必要」「法人が関わる場合は事前確認」などの条件がある。
  規約の文面をそのままユーザーに見せ、該当するか（個人か法人か、収益化するか）を判断してもらう。
- AivisSpeech の標準の声は ACML（Aivis Common Model License）で、営利利用可・クレジット任意。追加した声はモデルごとに確かめる。
- クレジットの文言は `project.json` の `credit` に入れ、概要欄に書く（`publish.md`）。
- 規約は変わる。**公開の直前にも確認する。** 自分の記憶や古い記録で「使える」と言い切らない。

## 声を調整する

`voice` の項目（`project.json`、または台本のトップレベルで回ごとに上書き）:

| 項目 | 意味 | 目安 |
|---|---|---|
| `speed` | 話す速さ | 1.0 が標準。講義は 1.05〜1.15 が聞きやすい。速すぎると用語が聞き取れない |
| `pitch` | 声の高さ | 0 が標準。±0.05 程度まで |
| `intonation` | 抑揚 | 1.0 が標準。平板に聞こえるなら 1.1〜1.2 |
| `pause` | 読点での間の長さの倍率 | 1.0 が標準 |

この回だけ別の声で試すなら `cv voice video <ep> --voice aivis:888753760`。

## 読みを直す

`voice` のあとに出る `out/<ep>/readings.md` で、エンジンが実際に読むカタカナを確認する。
「/」はアクセントの区切り、「、」「。」は間を表す。

- **1つの語の途中に「/」が入っていたら、区切りを間違えている**（例:「コンテン/トブ/ロックストップ」「ストッ/プリイズン」）。
  そのまま読むと不自然に聞こえる。対処は次の順で試す。
  1. 文を言い換える。前後の語が変わると区切りも変わる（「ポイント、ストップリーズンです」→「ストップリーズンの話です」）。
  2. 長い英語の名前なら、読むのをやめて役割を日本語で言う（`script-guide.md`）。
  3. 辞書の読みを、日本語として一般的な語形に寄せる（「サーバーセントイベンツ」→「サーバーセントイベント」）。
  読みに「・」を入れると、そこに間が入る。区切りは直るが、ぶつ切りに聞こえるので最後の手段にする。

- 用語の誤読 → `lexicon.json` に「表記: 読み」を足す。読みはカタカナで書く。
- その文だけの誤読（同じ漢字で読みが変わるもの）→ その行に `"read": "…"` を書く。
- **数字が1桁ずつ読まれる**（「HTTP 200」が「ニイゼロゼロ」）→ `read` で漢数字にする（「エイチティーティーピー二百」）。
  ひらがなで「にひゃく」と書くと、前後の区切りが崩れることがある。
- 直し方は `cv reading video "試す文"` で試す。音声を作らずに読みだけが出るので、何通りか比べられる。
  台本全体は `cv readings video <ep>` で、音声を作る前に下見できる。
- **カタカナの読みを辞書に入れると、かえって区切りが崩れる語がある**（ZDR、macOS など）。その語は、読みを空文字で登録する
  （`"ZDR": ""`）。置き換えずにエンジンに読ませ、「辞書にない英字」の注意も出なくなる。

### 実際に出た誤読（AivisSpeech）

台本を書くときに先回りして避けると、やり直しが減る。

| 書いた形 | エンジンの読み | 直し方 |
|---|---|---|
| 元のデータ | ゲンノ | `read` で「もとの」 |
| 次の（文頭や読点の直後） | ジノ | `read` で「つぎの」 |
| 空か | ソラカ | 言い換える（「空っぽか」など） |
| その上に | ソノカミニ | 言い換える（「さらに」など） |
| 10分の1 | ジップンノイチ | `read` で「十分の一」 |
| 肯定形 | コウテイガタ | 辞書に「こうていけい」 |
| 最適化者 | パーソナライズシャ | 辞書にひらがなで |
| 両方書きます | リョウホウガキマス | 助詞を入れる（「両方を書きます」） |
| 現時点 | ゲン／ジテン（途中で区切れる） | 言い換える（「いまの時点」） |
| HTTP 200 | ニイゼロゼロ | `read` で漢数字（二百） |
| LLM、SSE、XML タグ | エルエル／エム などと途中で区切れる | 声では言い換える（「モデル」）か、助詞を挟む（「XML のタグ」） |
| 長い英語の名前のカタカナ読み | 語の途中で区切れる | 声では役割を日本語で言う |
- 語の途中に不自然な間が入る → 読みの中の空白や読点が原因。`read` で空白を取る。
- アクセントの違和感は、この表ではわからない。ユーザーに聞いてもらい、気になる語は言い換えるか、ひらがな・カタカナで書いて試す。

## 別のエンジンを足す（有料の音声、自分の声）

ElevenLabs や VOICEPEAK などの有料音声、または録音した自分の声を使いたいと言われたら、`scripts/certvideo.py` に足す。

1. `synthesize()` は、エンジン名で `synth_say()` か `synth_compat()` を呼び分けている。ここに新しい関数を足す。
   関数の約束は「1文の文字列を受け取り、`dst` に音声ファイルを書く」こと。形式は何でもよい
   （最後に `to_standard_wav()` で 48kHz・モノラル・16bit の wav にそろえる）。
2. API キーは環境変数から読む。台本や `project.json` に書かない。
3. 有料の API は文字数で課金される。同じ文は作り直さない仕組み（`.cache/vo/`）があるので、
   台本の修正のたびに全文が再課金されることはない。それでも、**最初に実行する前に、文字数とおおよその費用をユーザーに伝える**。
4. 読みのカタカナ（`readings.md` の「エンジンの読み」）は、VOICEVOX 互換のエンジンでしか取れない。
   ほかのエンジンでは、渡した読みの文がそのまま表に出る。誤読の確認は、聞いてもらうしかなくなる。
5. 自分の声を録音する場合は、1文ごとの音声ファイルを用意してもらい、合成の代わりにそのファイルを読む関数を足す。
   文と文の間やタイムラインは、同じ仕組みで作れる。
