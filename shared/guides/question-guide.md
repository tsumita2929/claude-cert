# 練習問題の書き方

各試験フォルダの `data/*.json` が問題集の中身です。`python3 build.py` で検査して `index.html`（問題集アプリ）を作ります。ここでは、問題を書くとき・直すときの決まりをまとめます。

## 1. 目指す問題

本番の試験は、**業務の場面を示し、「最も適切な対応はどれか」を選ばせる**問題です。用語の暗記ではなく、判断を問います。公式の試験ガイドのサンプル問題（`reference/blueprint.md` の「問題の傾向」に要旨がある）と同じ型で作ります。

- **場面 → 制約 → 問い → 選択肢。** 問題文には、誰が何を作っていて、何が起きているかを書く。選択肢を絞り込む制約（「急がない」「監査が必要」「必ず守らせたい」「まず試す一手」など）や、判断材料になる数字（失敗の割合、件数、待てる時間）を入れる。
- **問いは最上級で聞く。** 「最も適切な対応はどれですか」「最も可能性の高い原因はどれですか」「最初に行うべきことはどれですか」。
- **正解は、原因に直接効く、つり合った手。** 誤答は「もっともらしいが劣る選択肢」にする。知識や経験が足りない人が選びそうなものを置く。明らかに変な選択肢は置かない。
- **誤答の型**（公式サンプルに繰り返し出る）:
  - 確率的な手で、必ず守らせたい問題を解く（プロンプトを強める、例を足すだけ）
  - 作り込みすぎ（別の分類モデル、新しい基盤。効くかもしれないが、最初の一手には重い）
  - 別の問題を解いている（論点がずれている）
  - 存在しない機能・設定・置き場所（もっともらしい名前のフラグや設定キー）
  - 適用範囲の取り違え（個人用と共有用、指示の置き場とコマンドの置き場）
  - 症状だけを抑える・下流を責める（原因は上流にある）
  - 両極端（握りつぶす／全体を止める、何でも渡す／何も渡さない、業務をやめる）
  - 規模で解決しようとする（もっと大きいモデル、長いコンテキスト、多数決）
  - 当てにならない目安に頼る（モデルの自己申告の確信度、文章の流ちょうさ）
  - モデルに頼んで済ませる（「保持しないで」「必ず守って」と指示するだけで、本当の管理策がない）
- **1問で1つの論点。** その論点が、試験ガイドのどの分野・タスクにあたるかを言えること。
- **正解は1つに決まること**（複数選択は2つ）。「どれも一理ある」中で、問題文の制約に照らすと1つだけが最善になるように作る。制約を書かずに「好み」で決まる問題は作らない。

避けるもの:

- 実際の試験問題、公式サンプル問題、ほかの対策サイトの問題の転載や言い換え（すべて自作する）
- 数字や名前の丸暗記を問うだけの問題。料金の金額、モデルの版の番号、上限値など、すぐ変わる数字を正解の根拠にする問題
- 「適切でないものはどれか」という否定形の問い（本番の型ではない。使うとしても全体の5%まで）
- 正解だけが長く詳しい選択肢。選択肢の長さと書き方をそろえる
- 「常に」「絶対に」のような言葉が誤答だけに付いていて、それだけで外せる選択肢
- 決まった言葉が正解にだけ出てくる選択肢。たとえば「確かめる」「照らす」が正解にだけ並ぶと、内容を知らなくても言葉で選べてしまう。誤答にも、「確かめてはいるが、相手・範囲・時機が違う」行動（Claude 自身に確かめさせる、一部だけ確かめる、出したあとで確かめる）を置く
## 2. 事実確認

- 正解の根拠と、誤答が誤答である理由は、**一次情報**（公式の試験ガイド、Anthropic の公式ドキュメント、ヘルプセンター、公式のエンジニアリング記事）で確かめる。調べ方と URL は `shared/guides/course-guide.md` の「2. 事実確認」と同じ。
- **自分の記憶だけで書かない。** あなたの知識より新しい仕様変更がありうる。
- その試験の `course/chNN.md`（講座の本文）ができていれば、末尾の「事実確認」の表を先に読む。同じ論点は、講座と同じ立場で書く。講座と食い違う内容にしない。
- **試験ガイドと現行のドキュメントが食い違う論点**（試験ガイドの発効後に製品が変わったもの）:
  - 正解は試験ガイドの立場で作り、`explanation` に「2026年11月時点のドキュメントでは〜に変わっています」と添える。
  - 食い違いが大きく、現行の仕様だと正解が変わってしまう論点は、問題にしない（報告する）。
- 誤答に「存在しない機能や設定」を置くのはよい（本番にもある型）。その場合は `notes` で「存在しない」と正しく説明する。実在する機能を「存在しない」と書かないよう、必ず確かめる。

## 3. 書式（`python3 build.py --check` が強制する）

`data/<ファイル>.json` は、問題の配列です。

```json
{
  "id": "D2-07",
  "domain": "D2",
  "scenario": "S1",
  "topic": "ツールの説明文",
  "type": "single",
  "question": "……最も適切な対応はどれですか。",
  "code": "（任意）設定ファイルやコードの断片",
  "options": ["……", "……", "……", "……"],
  "answer": [2],
  "notes": ["……", "……", "正解。……", "……"],
  "explanation": "……",
  "ref": "試験ガイド タスク 2.1 ／ Claude Docs: Define tools"
}
```

| 項目 | 決まり |
|---|---|
| `id` | `D<分野の番号>-<2桁の連番>`。担当ごとに使える番号の範囲が決まっている（ほかの担当と重ならないように） |
| `domain` | `id` の接頭辞と同じ（`D2`）。その問題の主な論点の分野 |
| `scenario` | シナリオ形式の試験（CCAR-F）だけ。`S1`〜`S6`。ほかの試験では書かない |
| `topic` | 論点の短い名前（12字くらいまで）。結果の一覧と、回答したあとの解説に出る（正解の手がかりになるので、アプリは回答の前には出さない） |
| `type` | `single`（選択肢4つ、正解1つ）か `multi`（選択肢5つ、正解2つ。問題文に「（2つ選択）」を入れる） |
| `question` | 場面と問い。2〜5文。です・ます体 |
| `code` | 任意。設定やコードを見せたほうが分かりやすいときだけ。改行は `\n` |
| `options` | 重複なし。「上記すべて」の類と、頭の「A.」などの記号は禁止。長さと書き方をそろえる |
| `answer` | 正解の添字（0始まり）の配列。**正解の位置は偏らせない**（担当分の中で、どの位置もほぼ同じ回数になるように） |
| `notes` | 選択肢と同じ数。その選択肢がなぜ正解か、なぜ劣るかを1〜2文で。正解の note は「正解。」で始める。誤答の note は「誤りです」で済ませず、どこが足りないかを書く |
| `explanation` | 全体の解説。3〜5文。判断の軸（なぜその手が最善か）を書き、ほかの場面にも使える形にまとめる |
| `ref` | 根拠にした一次情報の名前（「試験ガイド タスク 3.2」「Claude Code Docs: Memory」など）。URL は書かなくてよい |

- 文中の `` `…` `` は、画面で等幅になる。パラメータ名、コマンド、ファイル名、ツール名などコード上の名前だけに使う。
- 用語は、公式の日本語版試験ガイド（`reference/*_exam_guide_v1.0_ja.txt`）の訳語に合わせる。
- 複数選択（`multi`）は全体の15%くらい。「正しい説明を2つ選ぶ」より、「この状況で取るべき対応を2つ選ぶ」の形にする。
- シナリオ形式の試験では、アプリが問題の上にシナリオの説明を表示する。問題文でシナリオの説明を繰り返す必要はないが、その問題に固有の状況（何が起きたか）は問題文に書く。

## 4. 書き終えたら確かめる

```bash
cd <試験>    # リポジトリの直下から
python3 build.py --check data/<自分のファイル>.json
```

- エラーをなくす。表示される「正解位置 A-E」が偏っていないかを見る。
- 「択一で正解が最長の選択肢」の割合が25%前後か、「注意: 正解が誤答の平均より3割以上長い問題」が出ていないかを見る。出ていたら、誤答にも同じ細かさの具体的な内容を書き足すか、正解の言い回しを削って、長さと詳しさをそろえる。
- 自分で1問ずつ解き直す。問題文の制約から正解が1つに決まるか。誤答のどれかが、実は正解と同じくらい良くないか。
- 同じファイルの中で、論点や場面が重なっている問題がないか。
- **ほかの担当のファイルと `index.html` は書き換えない。**

## 5. 見直し（レビュー）をするとき

問題を書いた人とは別の目で、次を確かめます。

1. `answer` を見ずに解く。自分の答えと正解キーが合うか。合わなければ、どちらが正しいかを一次情報で決める。
2. 正解の根拠を一次情報で確かめる。誤答が、現行の仕様では正解になっていないか。
3. 正解が1つに決まるか（問題文の制約が足りているか）。
4. `notes` と `explanation` に誤りがないか。講座の本文（`course/chNN.md`）と食い違っていないか。
5. 正解だけが長い、誤答が明らかに変、といった「内容を知らなくても解ける」手がかりがないか。
6. 似た問題の重複がないか（同じ試験の全ファイルで）。重複は、片方を別の論点の問題に差し替える。
7. 公式サンプル問題（試験ガイドのサンプル問題の章）の言い換えになっていないか。同じタスクを問うのはよいが、場面、数字の置き方、4つの選択肢の型がサンプルと重なっていたら、言い換えにあたる。別の場面と別の誤答で、別の角度から問う問題に作り直す。

1 は、正解と解説を除いた問題用紙を作って、問題を書いた人とは別の担当（サブエージェント）に解かせ、あとで正解キーと機械的に突き合わせると確実（2026-11-18 の点検では、全451問でこの方法を使った）。

直しは直接ファイルに反映し、何をどう直したかを報告します。
